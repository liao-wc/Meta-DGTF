   🔥 │ 1 的一端把订单已被接收当作先于库存结算存在的事实。它的显现次序是：入口回执 → 订单出现 → 库存事后收敛。
   🔥 │ 两个“先”不一样，撞的是谁有权定义“已经卖出”。
   🔥 │ 
   🔥 │ 二、各推到极端
   🔥 │ 0 推到极端：全链路等一个库存主副本。每个 SKU 的余量更新成为全局节拍，节拍越准，入口越像队列。
   🔥 │ 1 推到极端：入口不再等库存。订单先以承诺形式扩散，库存结算退到后台。后台一旦追不上，超卖不是异常，是承诺与结算之间的时间差。
   🔥 │ 0 的代价集中在等待，1 的代价集中在追账。
   🔥 │ 
   🔥 │ 三、找反转点
   🔥 │ 反转点出现在入口回执离开库存权威的那一刻。之前，0 定义链路；之后，1 定义用户看到的事实。
   🔥 │ 另一个反转点：追账延迟超过可接受窗口时，1 的承诺会倒逼 0 的锁重新出现，只是锁的位置从数据库行移到了补偿队列。
   🔥 │ 显现的节奏是：先承诺，后追账，追不上，再收窄。
   🔥 │ 
   🔥 │ 四、让对撞生成新东西（不是折中，是生成）
   🔥 │ 对撞生成“承诺深度”：已对外发出、尚未与库存结算抵消的量。0 负责给它上限，1 负责给它流速。
   🔥 │ 再生成“结算延迟”：承诺发出到库存权威确认之间的时间。它不直接等于超卖，但承诺深度乘结算延迟会暴露超卖压力。
   🔥 │ 链路可据此分档：浅承诺深度时直接扣；中深度时用本地额度；深深度时只发排队凭证。档位切换看深度与延迟的乘积，不看瞬时 QPS。
   🔥 │ 这一步不是把 0 和 1 折半，而是让两个事实分处不同时间层，并允许后层追前层。
   🔥 │
