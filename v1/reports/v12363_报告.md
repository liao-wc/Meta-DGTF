## 二、故障注入：5 种真实故障的实测矩阵

打的层是 `client.chat.completions.create`（**不是** `LLM.call` —— 见 §六）：

| 故障 | 改前表现 |
|---|---|
| 抛 RuntimeError（网络挂） | 重试 → 抛 → 调用点记 `errors`（**留痕** ✓） |
| 内容为空 | 同上（**留痕** ✓） |
| **非 JSON 文本** | 内容非空、解析失败 ⇒ **当空处理、零留痕** ✗ |
| **`"null"`** | 同上 ✗ |
| 类型不对（该 list 给 str） | 调用点报错（留痕 ✓） |

**「答了但答不成结构」这一类静默丢失** —— 产物看起来只是"内容少"，
读的人分不清「模型不配合」与「题本身没什么可写」。这违反红线「失败留痕」。

## 三、修法一：`llm_bad_json` 出口

```python
# LLM.call 里，拿到非空内容之后
if json_mode:
    if self.parse_json(content) is None:
        self.bad_json += 1
        logger.warning("json_mode 但解析失败（累计 %d 次，stage=%s）：%r", ...)
return content        # ← 控制流一个字没动
```

产物顶层增 `llm_bad_json`；md 在 >0 时加一行：

```
- ⚠️ 模型返回了非结构化内容 3 次（要求 JSON 但解析失败）—— 这些环节走了兜底，
  读数可能偏低。这是留痕，不是缺陷判定。
```

**不改控制流**：解析失败仍走原兜底路径，只是这件事现在**有记录**。

## 四、修法二：`max_retries=0` 的脚枪

```python
for attempt in range(1, self.max_retries + 1):     # ← max_retries=0 ⇒ 空循环
```

⇒ 把 `max_retries` 配成 0（本意"不重试"）会让**所有调用必然失败**，
而且报错是 `LLM 连续 0 次失败: None` —— `last_err` 还是 None，看不出根因。

改成 `_tries = max(1, int(self.max_retries or 0))`：

| 配置 | 改前尝试次数 | 改后 |
|---|---:|---:|
| 3（出厂默认） | 3 | **3（不变）** |
| 1 | 1 | 1 |
| 0 | **0（必失败）** | **1** |

同文件的 `WebSearchGate` 本来就写 `range(max_retries + 1)`，两处语义现在一致了。
★ 没有去改「3 次 = 1 首试 + 2 重试」这个既成事实 —— 改它会影响成本与时延，属另一件事。

## 八、经验教训

1. **故障注入必须打"真正执行的那一层"**，否则测的是你自己换上去的东西。
2. **"内容非空"不等于"内容可用"** —— 校验层级要区分「有没有」和「合不合格式」。
3. **配置里的 0 要问一句"它的语义是不是'关掉'"**：`max_retries=0` 看着像
   "不重试"，实际是"不尝试"。
