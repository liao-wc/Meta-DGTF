### 三条全局红线

| 红线 | 判据 | 实测 |
|---|---|---|
| 不许删任何机制代码 | `count_del_lines`（纯删除块）+ `mechanism_removed`（AST 符号） | **0 / 0 项** |
| CRLF 一致 | 每份补丁脚本读写两次断言 + `crlf_ok()` | 纯 CRLF |
| 失败必须留痕 | 每个失败路径都要有出口 | 见各阶段报告 |

★ 口径说明：任务书原话是「`git diff` 里 `del` 代码行数必须为 0」。
但**同一份任务书**又要求改 `coverage_of` 签名、把 `_auto_plan` 正文搬到
模块级 —— 这些在 difflib 里是 `replace`（改写），不是 `delete`（删除）。
用「以 `-` 开头的行数」当判据会把改写也算成删除，结论恒为「违规」。
所以判据拆成两个数：**纯删除块 0**（红线）+ **改写 185 行**（如实报），
并且「机制有没有被拿掉」另按 **AST 符号**判（`mechanism_removed`）。
这是**判据口径的修正**，不是放宽——符号消失仍然一律判红。

### 六条踩过的坑（每条都由一次真实误判换来的）

1. **往已有 dict 加键前先看它在不在**：`as_evidence` 在
   `DEFAULT_CONFIG["external_anchor"]` 里**早就存在**，新值被后者静默覆盖
   → 新增全文件 AST 判据 `check_v122_dup_dict_keys`。
2. **子串锚点会把缩进插坏**：8 空格的注释锚点命中了 12 空格同名注释
   （前者是后者的子串）→ 替换发生在行中间 → `IndentationError`。
   锚点带前导空格时必须按**整行**匹配。
3. **docstring 里的 `def 名` 会被字面串计数当成定义**：
   「`_compute_rephrase_streak` 出现 2 次」其实是 1 定义 + 1 处文档提及。
   数实现一律走 **AST**。
4. **判据串要 copy，不要凭记忆拼**（本轮三次）：`render_landing` 改名、
   `_retrieve_anchors` 的抛错搬进 `AnchorRetriever`、探针里
   `view.errors.append(f"锚点冲突` 与实际落点不符 —— 三次都是判据串不对，
   不是功能没了。但**也要分清另一种**：`render_landing` 那条同时暴露了
   **真的信息丢失**（池级留痕只留在老模板）→ 抽成共用实现才算修好。
5. **硬约束 flag 会被 `quality_flags` 重算冲掉**：读**真跑的 packed** 才发现
   （`errors` 有、`quality_flags` 空）。读代码看不出来 —— 19 行的距离。
6. **「逐字一致」在这个引擎上不可达**：每步都是独立抽样。
   G6.4 靠**负对照**说清楚：跨版本差异 3927 行、**同文件重跑 5989 行**
   （比跨版本还大）→ 跨版本差异不含信号。判等价要看**结构化字段**
   （两侧一致）+ 阶段 6 的打桩对照。

## 九、全量回归结果

### 9.1 F.1 的设计（含一处**降档**，如实标注）

任务书 Step F.1 的原始档是「20 题 × balanced × `0:5,1:5,both:5,all:6`」。
按阶段 1 的实测单价（~1.6M token / 题、~50 min / 题），20 题约需
**¥80 与 5 小时以上**，超出本轮预算与时长。

所以 F.1 拆成两件事，**各司其职**：

| 目的 | 档位 | 题量 | 证据位置 |
|---|---|---|---|
| **深度**（分层目标 / 覆盖率归属在完整档下成立） | **原始档** balanced + 0:5,1:5,both:5,all:6 | 3 题（eng/biz/tech_001） | `bench/runs/p1v2/`（`v122_phase1_报告.md` 第六节） |
| **广度**（20 题都有产物、四列报告可生成） | **降档** economy + `0:1,1:1,both:1,all:1` | 20 题 | `bench/runs/v122_full/` |

降档这一事实**写进了产物本身**：`bench/runs/v122_full/index.json` 里有
`profile_override` / `rounds_override` 两个字段，报告头部也会照抄出来 ——
不是只在报告里口头声明。

### 9.2 广度回归结果

命令：

```bash
python bench/bench_run.py --src 元DGTF-V1.22.0.py --jobs 5 \
  --profile economy --rounds "0:1,1:1,both:1,all:1" --tag v122_full
python bench/bench_report.py bench/runs/v122_full > bench/reports/v122_full.md
```

结果见 `bench/reports/v122_full.md`（四列：**判定 / 一致率 / 分层 pass / rubric**）。

实测汇总：

| 指标 | 实测 |
|---|---|
| 产物 | **20 / 20**（eng/biz/med/law/org/tech 六领域全覆盖） |
| 四列报告 | 生成成功，报告头逐字标注降档（`profile 覆盖：economy` / `rounds 覆盖：0:1,1:1,both:1,all:1`） |
| **分层 pass**（4 行分层目标 + 四层 objective 全对） | **20 / 20** |
| 一致率 ≥ 50% 的题数 | **16 / 20**（中位 100%，最低 0% —— `med_001` 6 条全 low） |
| 调用数 min / 中位 / max | 52 / 54 / 97 |
| token 合计 / 单题中位 | 7 947 216 / 355 310 |
| rubric 非零的题数 | **2 / 20**（平均 0.10/3） |

两条要连着看：

1. **「分层 pass 20/20」是本阶段真正的交付**：分层目标四行、四层 objective
   映射，在 20 题 × 6 领域上都成立，不是只在那 3 题的样本上成立。
2. **rubric 只有 2/20 非零**，与第四节（阶段 3）的结论一致 —— 行动闭环的
   **效果**没达标，不是报告写错了。同一条数据在两处给出同一个结论，
   比任何单点读数都更可信。

★ 一致率这次有 20 个样本（不是阶段 2 的 3 个）：**16/20 ≥ 50%**，
4 题低于 50%（最低 `med_001` 0%）。这支持一个**谨慎的**说法：
三态多票在**多数**题上能把一致率推到中位 100%，但**不是所有题**都行 ——
按本项目 §7.13 的定性，这是标签本身的可定义性边界，不同题落在边界两侧。
仍不足以宣称「多票提高了一致率」，因为缺少 ON/OFF 对照。

### 10.3 口径 / 设计上要继续盯的

1. **`tier` 缺省 3 + `tier_floor` 缺省 2** ⇒ 不带 `tier` 的锚点一个也进不了
   引用表。刻意的保守默认，但需要在载入时给显式提示（现在只是静默不进表）。
2. **`auto` 取向的错配看不出来**：`render_landing` 对 `auto` 走 decision 模板，
   但产物里没有回填 `plan_orientation` 的真实判定结果，
   于是「auto 判成 boundary 却渲染 decision 模板」这种错配无迹可查。
3. **`budget.max_calls` 未被 harness 消费**（引擎按 `cost_profile` 定预算）。
4. **一致率的样本量**：阶段 2 只有 3 次真跑。按本项目已记录的经验
   （同条件两跑 calls 差可达 -10），**不能**据此宣称「多票提高了一致率」，
   只能说「没有把它做坏」。要宣称前者，需要 ON/OFF 各 ≥3 次的对照。
5. **`pending_fix` #1**：`auto_plan` 的**归一化规则**仍是两份
   （模式白名单 + 逐层钳位 + 中位数补漏 + 低置信退 serial）。
   本版收口的是「同一个函数」，不是「同一份规则」。
6. **`_extract_actions` 的动词归属粗糙**：一句里有两个白名单动词时取白名单
   顺序靠前的那个（实测把「委托…清淤」的 verb 判成「清淤」）。
   若继续走抽取路线，需要按领域把白名单配置化。
