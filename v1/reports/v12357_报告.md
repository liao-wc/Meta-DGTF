## 二、问题：判据在，通道断了

追查 A/B 里「`stop.gain_floor` 零触发」时，本以为要扫阈值（6/8/12，≈¥12）。
查下去发现**扫任何阈值都不会触发**：

1. `layer_gain_stop_signal` 第一道门：

```python
if len(_tr) < int(_LG_STOP_FLAT_N) + 1:      # N = 2 ⇒ 需要 ≥3 条历史
    return False, ""
```

2. `prev` 来自 `view.goal_trace`（`_goal_stop_signal` 里 `_tr = list(getattr(view, "goal_trace", ...))`）。
3. 而引擎**每圈新建 view** —— 串行侧 `view = dg.run(inp)`，旁边注释原话：
   「跨圈累积 view.errors —— **每圈新建 view**、只 return 最后」。
   `_layer_goal_now` 每圈 `view.goal_trace.append(...)` 追加到**当圈那个 view** ⇒ 下一圈就丢。
4. 产物实测（两臂八层全部如此）：

| 层 | `rounds_run` | `goal_trace` 条数 |
|---|---:|---:|
| 0 | 4 / 6 | **1 / 1** |
| 1 | 7 / 6 | **1 / 1** |
| both | 7 / 7 | **1 / 1** |
| all | 4 / 2 | **1 / 1** |

⇒ 停止判定那一刻 `len(_tr)` **恒为 1** ⇒ `1 < 3` ⇒ 键**永远不触发**。

> 这是「走得到」三种失败形态的第 ①种：**结构性不可达** —— 调用点在、逻辑对，
> 被数据流挡死。它比"没实现"更难发现，因为代码读起来完全正常。

**直接后果**：原计划的 `gain_floor` 取值扫描（≈¥12）会扫出三个「零触发」，
再被误读成「这个键没用」。**先证明它走得到，再谈它值多少。**

## 三、修法（只搬数据，不动判据）

```python
_hist = getattr(self, "_goal_hist", None) or {}
_h = _hist.setdefault(str(entry), [])
_h.append(_rec)
view.goal_trace = list(_h)          # ← 每圈把完整历史挂回当前 view
```

+ `run()` 起跑 `self._goal_hist = {}`（同一实例可能被复用跑多次，不清会污染本跑）。

三个决定：

1. **历史挂引擎、不挂 view**：view 每圈换新，只有引擎级容器能活过一圈。
2. **每圈挂回「完整」历史**（不是只挂最后 2 条）：判据自己会取最后 N 条，
   引擎不该替它裁剪 —— 否则将来判据要 5 条历史时又得改这里。
3. **`run()` 起跑清空**：交叉污染比"少记几条"更危险。

`gain_floor` 默认 0（关）⇒ 那条历史**根本没人看** ⇒ 出厂行为逐字不变。

## 六、经验教训

1. **「零触发」要分三种**：条件没出现 / 阈值太严 / **通道断了**。前两种可以调参，
   第三种调什么都没用。**先证明它走得到**。
2. **每圈新建对象时，跨圈状态必须挂在生命周期更长的地方。** 这一版和
   `_eml_finish` 的"按实例计数器"是同一类错误的两个变种。
3. **测「能触发」时，先确认测试路径能到达触发点。** mock 太温顺会让判据假红，
   然后你会去"修"一个没坏的东西。
