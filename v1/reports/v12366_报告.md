## 一、先修一个真 bug：anytime 停止判据反向

原实现（v1.23.63 起）在串行与 B 模式两处都这样写：

```python
anytime_decided([1 if new_amps > 0 else 0 for r in round_log], thr=0.5)
```

`anytime_decided` 的语义是“**多数已确立**”（下界 > 0.5）。把“本圈有新增结构”当 1，
等于：**多数圈还在长 ⇒ 判停**。而停止理由写的是“结构仍在长的下界已跌破 0.5”，
与代码正好相反。后果是：越在产出新结构的层，越容易被提前停掉 —— 这是质量风险，
不是成本优化。

**修法**：新增 `anytime_stagnant_decided(growth_seq)`，先把生长序列取反
（有新增→0，无新增→1），再判“多数不再长”。停止理由改为
“「不再长」下界 > 0.5”。两处调用点（串行、B 模式）同步替换。

判据边界（已测）：

| 序列 | 判定 |
|---|---|
| 12 圈全无新增 | **停**（True） |
| 12 圈全在长 | **不停**（False） |
| 6 圈全无新增 | 样本不足，不停 |
| 0/1 混合 | 不停 |

这样“停”的是停滞层，“不停”的是仍在产出的层；anytime 的任意停时有效性不变。

## 二、输出质量：严格 JSON 自修复

`json_mode` 下模型偶尔“答了但答不成结构”（旧版只记 `bad_json`，调用点走兜底，
内容直接丢）。v1.23.66 增加一次**低温修复调用**：

- 只在解析失败时触发（成功路径零额外成本）；
- 只修格式（引号/逗号/括号/围栏），不改语义；
- 修复调用计入 `ops`（自测量），不混进“任务本身”的成本；
- 计数器：`llm_json_repaired` / `llm_json_repair_failed`；
- 配置：`api.json_repair`（默认 false = 零行为差；本机 yaml 开 true）。

## 三、架构可观测：分环节成本 + 质量闭环

以前只有总 calls/tokens，读者无法回答“钱花在哪一环”。现在：

- `LLM.stage_stats()`：按 stage 汇总 calls / tokens / ms，线程安全；
- packed 新增 `llm_by_stage`、`llm_json_repaired`、`llm_json_repair_failed`；
- packed 新增 `quality` 块：覆盖率（分子/分母）、三态一致、决策动作数、
  not_do 数、各层质量线索/停止/发散态；
- md 新增“质量闭环”与“分环节成本（Top4）”两行。

这些是**读数**，不改输出；它们让下一轮优化有数据，而不是靠猜。

## 四、效率：池窗口也遵守 shape_limit

`spiral.shape_limit` 原来只作用于 `View.shape_of`；`_pool_text` 里硬编码
`[-8:]`。把配置调到 6/4 时，view 窗口降了、池没降 —— 配置看起来生效、成本没降。
现在池窗口同源：`shape_limit > 0` 时按它截，默认 0 时保持历史 8 条（零行为差）。
