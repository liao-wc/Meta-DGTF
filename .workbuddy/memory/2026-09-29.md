## 竞态复核（写探针 `_race_probe.py` 实测）

结论推翻了上一节只点名 D/E 的说法：
- **B/C/D/E 在 0/1 这一段完全等价**——0 层预热 1 圈后与研究层并行，
  研究层第 1 圈读 `self.pools["0"]`（v1.21.54:8070，**无锁**），
  修行层写池走 `_apply_view_to_pool`（5393，**有 `_pool_lock`**）。
  写原子 → 不会撕裂/崩溃；后果只是"读到第几圈之后的池"不确定 → 不可复现。
- **B/C 的并发面其实比 D/E 更宽**（四层全并行 vs 只有 0/1 并行），
  所以按竞态论 B/C 更该被点名，不是 D/E。
- **B 有个设计缝**：B 号称下游读"上一波定格"（`_prev_results`，view 引用
  不变），但研究层的池分解读的是**当下活池**，绕过了定格语义。
- **mock 里这条路径根本没触发**：`_has_pool_content_view` 唯一一次调用
  返回 False（mock 的 0 层 view 是空壳），九个模式全部走了"外部评估"。
  → 冒烟表里的"判定源 pool+external"是 `decidability_source`，
    跟 `decompose_source`（研究层子问题分解）是**两个字段，别混**。
  → 真实 API 下 0 层 view 有内容才会走池路径，mock 验证不了这段。
- 消除办法：用 F/G/H；或 warmup ≥ 0 层 hard_max；或给读路径加快照/锁。

### 竞态的影响面（答 aL「是一圈还是整层」）
- **窗口只有一圈**：`_b_pre_layer` 里 `if r != 1: return` + `not sub_questions`
  双门槛，只在研究层第 1 圈开头读一次池（= 一次 decompose LLM 调用）。
- **影响是整层 + 下游**：`sub_questions` 生成后**不再重算**，被每圈 prompt
  （3233）、覆盖率/停止判据（5783）、终局清算（974/999/1014/1155）消费，
  再经研究层产物传给 both/all。即"一次性竞态，持久性后果"。
- **修行层不受影响**（它只写）。
- **触发概率其实低**：写池在圈末、读池在圈首，中间隔着修行层一整圈；
  只有"研究层 decompose 那次调用期间修行层恰好收工写池"才撞上。
- **不会崩**：写有锁、读是 list 切片；最坏是混合快照（probes 来自 r2、
  amps 来自 r3），因为 `Pool.merge` 是多段 append 循环而非原子替换。

## 九模式实测对比（v1.21.54，测量脚本 `_cmp_modes.py` 已保留）

度量方式：打点 `_run_one_round_B`（serial/A 走 `_run_layer`，粒度是层）
记每圈 start/end，算 work（各圈耗时之和）/ span（首圈→末圈）/ 峰值并发 /
下游开跑时已吃到的上游圈数。

加速比（work÷span，mock 四层各 2 圈）：
serial 0.99 / A 1.76 / **B 2.12** / C 1.44 / D 1.25 / E 1.11 / F 1.25 /
G 1.10 / H 1.08。峰值并发：serial 1 / A 3 / B 4 / C 3 / D·E·G·H 2 / F 3。

**结论（反直觉，值得记住）**：C 并不比 B 快，反而慢不少。
原因：C 的闸门是链式的（both 等 1 首圈、all 等 both 首圈），首圈要
一节一节排队；B 是 0 层预热一圈后四层一起冲，没有首圈链。
D~H 更慢是因为硬闸（等整层跑完）更多。
真实场景每圈几十秒、all 层还多 1 圈，这条链只会更疼 ——
"要快"默认选 B 而不是 C。

上游新鲜度（下游第 1/2 圈开跑时上游已交出的圈数 0/1/both）：
- B：both 吃 1/0、2/1；all 吃 1/0/0、2/1/1 —— 上游永远差一圈
- C、F：both 只吃到 1 的第 1 圈（2/1）
- D、H：both 吃满 2/2，all 首圈吃 2/2/1
- E、G：all 吃满 2/2/2 —— **E 是语义最完整的并行档**（代价是最慢之一）

健康指标九档全绿：self 四层齐全、判定源 pool+external、care 8、
输入自检 1、无缺项、无配额超限。
调用数 serial 79 / A 89（多一个汇流圈）/ B 78 / C~H 76。

## cost_profile 收尾：合并展开的健壮性修复 + 三档产物结构验证

**发现并修掉一个真实风险**（不是设计问题，是实现漏洞）：
`_expand_pair_merged_once` 原先在模型不输出「----阳----」分段标记时，
把整段都当阴、阳段置空 —— **会静默丢掉整个阳视角**。
自测时 mock 恰好不遵守标记，才暴露出来（economy 表现为只展开阴）。

修法（两层）：
1. **补跑兜底**：没标记 → 补跑缺的那半边（用 prompt1 的完整版），
   而不是丢弃。最坏退化成原来的两次调用（成本不亏），永不丢内容。
2. **标记加强 + 容错解析**：标记改成更醒目的 `===== 阳 =====`，
   prompt 里写明「那一行除了标记不许有别的内容，改了就切不开」；
   解析加一层正则容错（整行只含阳字与符号也认）。

**实测证据链**：
- mock 不守标记时 economy=78（补跑生效，比 69 多 9 次 = 每圈每层补跑）
  → 证明兜底真的在跑，不是摆设。
- 让 mock 也守标记后 economy 回到 69 → 证明主路径（命中标记、不补跑）通了。
- 冒烟加 `check_merge_fallback`：断言缺标记时必须补跑（2 次调用）
  且阴阳两段都在。
