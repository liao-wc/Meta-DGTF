# 元 DGTF 项目 · 长期约定

## 项目形态

- 单文件 Python 程序（`元DGTF-V1.21.xx.py`），无包结构、无测试框架依赖。
- 一个"元 DGTF"引擎：四层（修行 0 / 研究 1 / 对撞 both / 元 all）× 螺旋跑圈，
  三通道记忆（content / context / self）。
- 核心构思（改代码时的红线）：
  - 输入是**形状**不是数据；悬置不打分；未对齐（unaligned）是合法结果
  - 停止与清算分开；失败必须留痕；入池前挡重复；参数按层可覆盖
  - 自省（self-check）是**另一个视角**，不能和别的步骤合并掉

## 版本迭代约定（每轮都这么做）

1. **不覆盖源文件**：每轮从上一版**复制**出下一版（如 56 → 57），
   旧版保留为定稿快照。
2. **版本号两处**：文件第 5 行标题 + `__version__ = "1.21.xx"`。
3. **changelog 在模块 docstring 里**，按版本分段、**最新在最前**。
   每段写「相对上一版改了什么」+ 实测证据 + 核对后未采纳的条项。
4. **冒烟**：`smoke_test.py` 的 `SRC` 指向当前版本，跑 9 种并行模式
   （serial / A–H / auto）+ 各版本新增的单元断言。
5. **真跑验证**：改完关键机制要跑真模型（见下），产物落 `outputs/`，
   verbose 日志落 `cost_*_run.log`，然后写分析报告（.md，编号分节）。
6. **收束**：一轮结束时给该版加「收束摘要」段（交付物 / 验证覆盖 /
   已知遗留 / 经验教训），下一版 changelog 顶部留"本轮尚未开始"占位。
   ★ 开版脚本的**锚点要落在可预期的位置**：56→57 那次锚在
   「★ v1.21.56 收束摘要」，而它恰好在文件最顶部，所以插对了；
   57→58 同样锚在「★ v1.21.57 收束摘要」，但它已落到第 333 行，
   于是 58 段落插进了中间。**别只断言"文本存在"，要断言插入后的
   块顺序**（脚本里打印一遍 `v1.21.* / ★ v1.21.*` 的行号序列核对）。
7. **分隔线是 U+2550 `═` / U+2500 `─`（各 60 个），不是 ASCII 的 = 和 -**。
   脚本里按 ASCII 拼会 assert 失败。

## 真跑（真模型）怎么做

- `.env` 里有 `DGTF_API_KEY`（35 位，sk- 开头）和 `DGTF_BASE_URL`
  （deepseek 官方）。**别打印 key 明文**，只看变量名/前缀。
- 后台跑用 wrapper 脚本：`load_dotenv(".env")` → import 元DGTF 模块 →
  `MetaDGTF(cfg).run(...)` → `contextlib.redirect_stdout(log)` →
  `save_result` → 把 `llm_calls`/耗时/产物路径追加进日志再落盘。
- 一次 3 圈 × 四层的真跑约 **100–135 次调用、15–18 分钟**。
- 跑完**主动查**（用户明确要求过），别干等后台通知。

## 已知的坑（踩过）

- **docstring 里写字面反斜杠会被转义**。changelog 在 docstring 里，
  写代码示例时若用 `\n` 之类，docstring 内容就和文件原文不一致，
  会让「摘 docstring 再扫源码」的断言失效。要写就写两个反斜杠。
  ★ **它的症状很误导（v1.21.59 收束时又踩一次）**：`src.replace(mod.__doc__,
  "")` 一失效，源码扫描类断言拿到的是**没摘 docstring 的全文**，于是
  「这几个旧写法必须已消失」的历史检查会**突然误报**（当时报的是
  `_mi_effective` 仍在用、调用处仍写死 0.3）。**看到"历史遗留检查突然复活"
  就先查 docstring 里有没有单反斜杠**，别去改业务代码。
- **扫源码断言要先规范 CRLF 再摘 docstring**：文件是 CRLF，
  而 `mod.__doc__` 是 LF，直接 `src.replace(mod.__doc__, "")` 匹配不上。
  正确写法：`src.replace("\r\n","\n").replace(mod.__doc__ or "","")`，
  再去掉以 `#` 开头的行。
- **统计产物时先确认提取边界**：manifest 里含 `## 一、…` 之类的二级标题，
  用"找下一个 `## `"定位章节末尾会被提前截断（曾把 4 条 self 误读成 1 条）。
- **「同一条逻辑两条跑圈通道各写一份」是本项目的高频问题**：已出现 4 次
  （跨圈去重、`_flag_all_drift`、覆盖率段、以及每次改动都要改两处）。
  新增跨通道逻辑前先问：有没有统一收口点？（`MetaDGTF.run` 的收口处
  是个好位置——所有并行模式都经过它一次。）
- **判「某改动影响了历史结论」之前必须实测复核**，别靠推断。
  曾靠推断说一个 bug 影响了 economy 的结论，实测后被推翻。
- **别用 `sed -i` / `awk` 就地改主文件**：主文件是 CRLF，`sed -i` 会
  把整个文件转成 LF（踩过两次）。改内容用 Edit 工具（它能保住 CRLF）；
  非要用脚本写，写完立刻核对 `s.count("\n") == s.count("\r\n")`。
  同一个坑还有：用脚本重建主文件时忘了写 CRLF（v1.21.57 重建时踩过）。
  ★ **还有一条同源坑（v1.21.59 踩）**：脚本里做**多行字符串替换**时，
  `open(p, encoding, newline='')` 读到的行尾是 `\r\n`，`split('\n')` 之后
  每行都带一个 `\r`，所以按 `\n` 拼出来的 `old_string` **永远匹配不上**。
  正确姿势：`raw.replace('\r\n','\n')` → 替换 → 写回时
  `s.replace('\n','\r\n')`。（好在断言 `count==0` 会当场拦住，不会静默改错。）
- **分档/停止类阈值的改动要先确认机制真的被触发过**：v1.21.58 做过一次
  `max_uncovered_pushes` 1 vs 0 的 A/B，结果 A 臂里该旋钮**一次都没机会
  起作用**（唯一的 fix-88b 事件落在最后一圈，被新守卫直接放行）——
  这种 A/B 只能测到噪声。**做对照前先确认操纵量在当前条件下可达。**
- **判定类状态不许定成"终审"**（v1.21.59 定）：可判定性、停止理由、
  债务状态这一类"分类/判决"字段，必须是**当前值 + append-only 履历**，
  允许被新证据推翻——**两个方向都要开**。旧实现只有
  `decidable→undecidable` 一条腿且没有回写路径（等于终审），
  导致 v59 整层交白卷。
  · 「有足够证据」必须落成**确定性校验**：要求引用的东西**此刻真的
    在池里**（编号 `A#/P#/T#/S#/C#/ing` 或原句模糊匹配），
    定位不到就**驳回并留痕**——不靠 prompt 恳求。
- **真跑批次可以 `run_in_background: true`，但别指望还能追**（v1.21.60 踩，
  2026-10-01 实测修正）：
  · **旧记载说反了一半**，当时写「进程在本轮结束时会被回收、唯一活的是前台跑」。
  实测：一批 2 次真跑（set_a/set_b，各 ~15 分钟）用 `run_in_background` 起，
  跨了多个对话轮 —— **两个 run 都跑完了**，产物和日志都在。
  · 真正失效的是**追踪句柄**：`TaskOutput` 回头查时报 "Background task not found"。
  进程没死，丢了的是句柄。
  · 所以正确姿势是：**起了就别再问 task_id，改看进程和文件**
    —— `tasklist | grep -c python` 看进程数，
    `ls -la <log>` / 产物 mtime 看进度。
  · ★ **`_run_v60.py` 是跑完才写日志**，跑的过程中 `ls v60_*.log` 查不到文件
    是**正常的**，别据此判它死了（2026-10-01 差点误判一次）。
  · `nohup ... &` 那条记载仍成立：调用一结束就被沙箱清掉，别用。
  · 启动后除确认进程数，还要**等第一个产物/日志出现再信**（约 15 分钟）。
- **要给人看的窗口**：PoSh 工具的
  `Start-Process -FilePath "<项目>\_watch_live.bat" -PassThru` 可行，
  窗口能跨调用存活。★ 但 **PoSh 工具常把输出吞掉**（只回
  "Command completed with exit code 0"）——**不能拿"没输出"当"没执行"**；
  验证要么 Out-File 到文件再 Read，要么从 Bash 用 tasklist 看进程。
  反过来，Bash 里**出现 shell 全名那个词就会触发安全拦截**，
  查进程用 `conhost` / `cmd\.exe` 代替。
- **判「真跑是不是卡死」不要只看日志字节数**：一次 LLM 调用几十秒不打字，
  12 秒零增长是正常的。要看 **≥45 秒**窗口，并确认**层/圈标记**有推进。
  · 反向也要有代价：不然它就退化成"为了让指标好看而翻转"的旋钮。
- **"只升不降"的指标是自欺**（v1.21.59 定）：覆盖率曾写成
  `max(cov_before, cov)`，把下降全抹平。但分母本身会变（判定可转移）
  → 比值**不可比**，正确做法是：**分母变的那一圈只重置基线，
  不计停滞也不计改善**（否则"新挂上一条可判定子问题"会被误判成停滞、
  "改回去"会被误判成进步）。见 `ChannelTracker.note_rebaseline`。

## 跑批（真跑验收等）约定（v1.21.60 定，用户拍板；2026-10-01 补实测）

- **多 run 并行一起跑**，按测试需求挑模式+题面。理由：瓶颈是 LLM 网络延迟
  不是 CPU；5 个 run 顺序 116 分钟，并行可压到 30–40 分钟。
- **★ 这是已拍板的默认做法，不要退回去写 `for` 循环串行**。
  2026-10-01 验收四跑时图"环境一致"写成了串行（估 60 分钟），
  用户问「4 跑是并行跑的吗」才发现退回了旧做法 —— 已 kill 重起。
  要"条件一致"就让**所有样本都并行**，而不是全串行：并行本身不构成混杂
  （三态判决是单次 LLM 调用，不依赖跨 run 状态）。
- 成熟 runner 是 **`_run_parallel_batch.py --max-concurrency N`**
  （ThreadPoolExecutor，任务项 `<mode> <rounds> <tag> <question>`，
  默认并发 3；注释里"第一次并行别设太高"那条早过期了，本项目已跑过
  数百份产物，4 并发实测无 429）。
- **但必须加并发上限 + 先小规模实测限流**：DeepSeek 的 RPM/TPM 未知
  （代码没配置、从没探测过）。证据：8 份日志 0 次「调用失败/429/限流」，
  但那都是 1x 并发。多 run 并发会不会撞，没测过。
- **限流 vs 降级，判别方式完全不同**（2026-10-02 实证）：
  · **限流**会明确回 429，代码有 `max_retries=3 + retry_backoff=1.8` 的
    指数退避扛得住 —— 表现是「变慢」，能自愈。
  · **降级/超时**不回错，直接挂着。`timeout=240` 加上外层 3 次重试 + 退避，
    **一次调用能烧十几分钟然后还是失败**；下游又有宽 `try/except` 兜着，
    于是外部看到的现象是**卡住且不报错**。
  · 所以「批跑是不是还活着」**不能只看进程在不在**（Process 在≠在推进），
    要看：有没有新产物/新日志、以及**单次调用的往返时间**是否回到基线。
  · **起大批量之前先跑一个 pilot 单跑**，确认通道正常并拿到基准耗时，
    别一上来就二十几跑 —— 通道挂的时候，跑得越多烧得越快。
- **卡住时的排查顺序**（这次有效，以后照做）：
  ① 查余额 `/user/balance`（欠费的表现可能不像是欠费）
  ② 查其它端点（`/models`、鉴权类）—— 能秒回说明不是网络也不是 key
  ③ **把自己的进程全杀干净再测**（排除自我拥塞）
  ④ 换回老 ID、去掉新加的参数（排除自己改出来的）
  四条都排除后才好意思说是服务端的事。
- **杀 python 进程的正确姿势**：`taskkill /F /PID <id>` 在 Git Bash 里
  常拿不到输出；用 PoSh 的 `Get-Process python | Stop-Process -Force`。
  PoSh 工具吞输出，验证要把结果 Out-File 到文件再 Read。
- **实现形态（待写 `_run_parallel_batch.py`）**：任务清单（模式+圈数+tag+题面）
  + `--max-concurrency N`（默认 2–3），每个 run 独立 subprocess、独立日志落盘，
  跑完汇总。内部 A–H 模式本身已用 ThreadPoolExecutor 做层内并行（10458/10601/10708），
  这是叠在它之上的第二层并行。

## 改后自检：怎么查「违背事实 / 忽略全局改错」（v1.21.60 教训）

任何"往一个方向拧"的修复，都可能拧过头、把另一方向的事实抹掉。改完必须
双向自检，四步（本次池评估修复就是这么被用户逼问出来的）：

1. **双向锚点测试**：别只放"明显可判定的题"验一个方向。同时放两类极端清晰的
   锚点题——纯事实题（锚 decidable）+ 纯不可判定题（锚 undecidable）。
   两道都判对才算没偏；只验一个方向 = 睁一只眼。
2. **看理由，不只看标签**：判定对不对不能只看 final 标签，要看它列的
   aspects/理由是不是**题目的真实内容**，还是机制产物（&印记 / ing 撞不动 /
   悬空线头这类任何题都有的）。判 decidable 时也要反查：它有没有把真实的
   不可判定部分硬说成可判定。
3. **分叉先问歧义**：两个评估器（外判 vs 池判）分叉时，先问"题目本身有没有
   歧义"，再判断谁对。分叉 = 信号（题有歧义），不是 bug。**不要默认"哪个
   符合我预期哪个就对"**——这是最容易犯的。
4. **查反向漂移**：修复往一个方向拧（如"少判 partial"），拧完专门查它有没有
   把"真该 partial/undecidable 的"也拧走了。过度修正的典型症状就是
   "一个方向修好了，另一个方向被牺牲"。

★ 铁律：验证测试样例**不能预设答案**——先问这道题**真实**的可判定性/期望值，
再判断系统判得对不对。预设答案会让人为了证明"修复成功"而忽略全局。

## 测量学：压扁器会伪装成稳定性（2026-10-01，最贵的一条）

**任何时候宣称「某指标很稳」，先确认它不是被某个后继机制压出来的。**

实证：覆盖率分母（`Y`）在 debug 前看着极稳（4/4/4/5，极差 1），冻结之后反而
分散（4/4/5/6，极差 2）。原因是 `_starve_escalation` 是一台**统一压缩机**：
不管上游判决给出多分散的起点，它连着饿 N 圈就把所有没答的条推到同一界 ——
不同跑于是被压成同一个数。看到的「稳」是机制的输出，不是被测对象稳定。

推广三条：

1. **低方差不等于可靠，它可能只是被过滤过了。** 拿到"方差小"先看它的下游
   有没有某种 clamp / fallback / 兜底在压尾；这类环节通常写在"健壮性"的
   名义下，动机完全正当，因而极难被当成嫌疑。
2. **想测上游就要把下游摘掉**，不是把下游调好。本轮的冻结分母（`_decided_answerable`）
   就是这个思路：**在被污染的字段之外，独立留一份上游快照**，让上层我只认
   快照。这也是比"关掉机制"更好的做法 —— 机制本身正当，关掉是退化。
3. **改观测口径后比 baseline 变差，往往说明改对了。** 本次预判写死在跑之前：
   "预期是覆盖率变差，若反而普遍变好说明改错了地方"，结果 100%×4 →
   84/90/100/97。堵掉"把答不上来的划出分母"的路径，数字就该难看。
   **跑之前把预判写进文档**，跑完才不会拿"看起来进步了"自我安慰。

## 工作区清理：什么是绝对不能删的（2026-10-01 定）

用户要求清临时文件时，**下面两类是原始数据，永不进待删清单**：

- `outputs/` —— 历史产物（400+ 份 md）。所有统计分析的地基。
- 顶层 `*.log`（尤其 `v60_*.log`，75+ 份）—— `_convergence_matrix.py`
  的**唯一数据源**。§7 那几张表全从这里抽，删了就再也算不回来。

可安全删（能重生）：`__pycache__` / `smoke_outputs`（冒烟落盘目录，
只有写没有读，`grep -rln smoke_outputs --include=*.py` 只回 `smoke_test.py`）。
2026-10-01 清了一次，`smoke_outputs` 当时已攒到 **9330 个文件 / 25.6 MB**
（9/29 起每次冒烟落几十份）——**它就是最大的垃圾源，每隔一阵该清**。

★ 顺手记一个判断技巧：`ls -la --block-size=K` 显示的 `0K` 是**四舍五入**，
不代表文件为空。拿 `v61_*.log` 六个文件举例，看着是 0K，实际有内容。
判空用 `f.stat().st_size == 0`，别用 `ls` 的列。

## 9 模式时序（准确版，别再凭印象）

**可判定性评估**（v1.21.60⑩ 起，已无「起跑前全局快照」）：唯一确定点是
`_assess_decidability_dynamic`，在**研究层第 1 圈拆解时**动态做——读 `self._results["0"]`
有产物→池评估（merge 外部），没产物→外部。读到哪就是哪，跟着拆解源走。
**0 层先行**（`_warmup_and_assess`/`_run_zero_then_assess`，只负责"跑 0 层"，不评估）：
B/C 预热 1 圈；F/G/H 跑满 0 层（下游硬闸 `("0",)` 等收工）；**D/E 不预热（0/1 双起并行，
评估源是竞态：0 层先交出第 1 圈→pool+external，没交出→external，两种都合法）**；
serial/A 跑满 0 层。0 层先行策略由 `_MODE_GRAPH` 推导，不硬编码模式名。
层调度先行（`_MODE_GRAPH`，谁先动）是**另一件事**，别混：
- serial：0→1→both→all 严格串行
- A：0 跑满 → 1/both/all 三者全量并行（`_upstream_provider=lambda e:[]`）
- B：轮次并行，四层齐步（0 领先 1 圈，一波一圈）
- C：流水线，每层比上层晚 1 圈（读活表非定格）
- D：0+1 双起 → both 等 0+1 满 → all 等 both 一圈
- E：0+1 双起 → both 等 0+1 满 → all 等 both 满
- F：0 先行 → 1 等 0 满 → both 等 1 一圈 → all 等 both 一圈
- G：0 先行 → 1 等 0 满 → both 等 1 一圈 → all 等 both 满
- H：0 先行 → 1 等 0 满 → both 等 1 满 → all 等 both 一圈
铁律：both/all 永远在依赖链下游，不可能先行；只有 0/1 能起头（D/E 双起，其余修行先行）。
快慢：serial 最慢；A、D/E 最快；B 受最慢层拖累。

## 跑批与信号传递的几条硬纪律（2026-10-02）

### 测试桩的签名落后于生产代码会**静默**失败

改 `LLM.call` 加了 `thinking=` 参数后，冒烟里的 `fake_call` 收不了 →
reasoner 调用 TypeError → 被业务代码 11531 的 `except Exception` 吞掉 →
现象是「汇流圈没跑」，而不是报错。**中间那一层宽 try/except 是失联的原因**。

规则：给任何带 `except Exception` 的高层流程喂参数时，**先 grep 一遍测试桩
和 wrapper 的函数签名**。已补 `check_thinking_wiring` 做回归，并把
`mod.LLM._real_call` 存下来，好让测试能直接验真实 kwargs（不联网、换假 client）。

### 换 model ID 之前先验等价性，别只看「能返回」

能返回 ≠ 你要的那个。**第一步看 `resp.model`，不是看你请求里填的名字。**
再补一组可判分任务（含 JSON 结构化这种真实用法）新旧对照；
只有这两者都对上，新一批数据才配拿来跟历史数据比。

### V60_* 环境变量覆盖必须在 load_config **之后**显式改 cfg

`_deep_merge` 会让 yaml 覆盖 env（文档注释写反了，见 §7.18⑤）。
所以 `V60_ROUTE` / `V60_MAX_CALLS` / `V60_THINKING` 都是 load_config 之后
直接改 `cfg[...]`，**不要依赖环境变量合并**——否则覆盖会被静默吞掉，
实验按错的配置跑完，事后才发现。

### 多因子塞进一批时，必须做成析因而不是「混着跑」

用户要求「thinking 也放进这一批」。混着跑事后分不清差异来自哪个因子。
正确做法：**完全交叉 + 随机化顺序**（时间混杂是本项目实打实踩过的），
每单元 ≥3 观测。且用**几道不同的题**当重复而不是同一题跑多次——
既估方差又让结论跨题成立（随机区组设计）。
