## 04:10 mx batch01 中途遇阻：补全通道超时（不是我们的问题）

### 现象

24 跑只完成 **1 跑**（`mx_eu_B_r6555_t0`，187 calls / 1,423,944 tokens / 11.6min，03:26 出的那份）。其余 3 个 worker 从 03:14:32 起到 04:00
没有新日志、没有新产物。

### 逐条排除（按顺序做，别跳）

1. **欠费**？不是。`/user/balance` 秒回：
   `is_available=True, total_balance=59.10 CNY`（topped_up 59.10、granted 0）。
2. **我们自我拥塞**？不是。把 4 个 worker **和** effort 探针全部杀干净
   （python 进程数归 0）之后再测，仍然超时。
3. **我们新加的 thinking 参数把请求搞挂了**？不是。不带 `extra_body` 的裸请求、
   以及老 ID `deepseek-chat`，一样超时。
4. **网络本身**？不是。TCP 握手 0.06s 正常；鉴权类端点秒回。

→ 结论：**只有 chat completions 这一条通道降级**，服务端侧。

### 处置

- 停掉全部 worker，**不让它继续空烧** —— 超时会被 `LLM.call` 重试 3 次，
  每次最长 240s，加上退避，一次调用能烧十几分钟然后还是失败。
- 起了探活 watchdog（`_watch_api.txt`，每 75s 一次），恢复第一时间能看到。

### ★ 教训（写进 MEMORY.md 了）

- **「并发 4 实测无 429」这条旧结论过期了**：这次不是 429，是**超时**。
  两者的判别方式完全不同：限流会回 429 让你重试（代码有指数退避，能扛）；
  超时是会静默地按「失败」处理，而 `max_retries=3 + timeout=240` 的组合
  会把每一次失败放大成十几分钟 —— **下游有宽 try/except 时，外部就是卡住
  不报错**。以后「批跑是不是活着」不能只看进程在不在，要看**有没有新产物/
  新日志**，以及**单次调用的往返时间**。
- 起大批量之前先跑一个 **pilot 单跑**确认通道正常+基准耗时，别一上来就 24 跑。

## 09:32 修掉可判定性标签偏乐观（负向探针揪出的那个毛病）

### 根因定位

外部判定器 `_assess_decidability`（元DGTF-V1.21.61.py:5092 的 system prompt）
把「问题在世界上有没有答案」当成「我可判定」——张三确实吃了早餐、路由器

### 修法（最小改动，只改 prompt 文字不动逻辑）

1. 「不可判定的特征」加第 5 条：**信息不足**——无渠道获得具体答案
   （某人早餐、某人 Wi-Fi 密码），查不到就归不可判定，不因"世界上有答案"
   判可判定。
2. 「关键原则」加一条：判断的是「你（评估者）现在能否得出答案」，不是
   「世界上有没有客观答案」。答案只能靠访问不到的外部事实 → undecidable。

### 验证（单步，3 次 LLM 调用，不重跑完整批）

| 2038 世界杯冠军（对照） | partial | partial（原始 undecidable，归一化后因列了「赛制规则可判」转 partial，合理）|

## 13:33 纠正 auto_plan 里「降级 mode」的无数据断言（用户批评）

用户：「请纠正之前的错误改动，之前就有跑过不同的模式，没用数据支撑你为什么在

### 错误定位

auto_plan 的 mode prompt 里有两句**没有数据支撑的断言**：
- 「★ 别在 mode 上找钱：并行方式动的是零头」——batch01 只测了 calls 上 mode
  差 -5.4%，但 tokens 上 mode B 是 A 的 2.03 倍（未坐实但方向显著），「零头」

1. 「别在 mode 上找钱」→ 诚实标注：calls 差 -5.4%（<10% 不构成主成本旋钮）、

### 教训（重要）

**写进 prompt 的每一句「断言」都必须有数据支撑**，否则就是「无意义的词」——
它不只是没用，还会通过「降级引导」污染调度（这次就把 auto_plan 掰成了偏 A）。
「别把 X 当质量手段」这种否定断言，必须建立在「测过 X 不影响质量」的基础上，
没测过就只能写「未测过」，不能写「提不高」。
