# v1.23.35+ 方案 · 联网全面化：按需 · 可控 · 自学习 · 运行中动态调整 · 全链路可追溯

> 用户指令（原文）：「不设限，每个层每圈每个环节都可以按需进行联网检索来作为论据，
> 但都可控，并且纳入自我学习迭代，并可以在运行进行中动态调整，同时检查每个逻辑
> 行为是否都可追溯，并纳入自我学习迭代范围，供元DGTF自我调度和运行中自我调整。」

## 一、需求拆解（6 条，逐条可验收）

| # | 需求 | 可验收的形态 |
|---|---|---|
| 1 | **不设限**：每层 / 每圈 / 每环节都可**按需**联网 | 框架支持**任意环节**声明需要查证；不是固定 7 个 stage |

## 三、设计（四件事，都是加性、默认零行为差）

### 3.1 ★ 核心：**统一的「按需查证」协议**

**问题**：31 个环节的输出格式各不相同（自由文本 / JSON / 结构化尾块）⇒ 无法用一套
schema 统一要求。**硬编码 29 个 stage 更是灾难**（每加一个环节都要回来改清单）。

**设计**：**两种声明形态 + 一个统一裁决**。

| 形态 | 适用环节 | 做法 |
|---|---|---|
| **A. 结构化声明** | JSON 输出的环节（判定 / 裁决 / 探针） | schema 加**可选**字段 `"web_queries": ["..."]`（**不给就零变化**） |
| **B. 尾块声明** | 自由文本环节（`_ing` / `_re_anchor` / `_expand_pair`…） | 允许输出 `===WEB-NEED===` + **一行 JSON**（与既有 `===ING-STRUCT===` 同规矩） |

**统一裁决**（引擎侧，**唯一实现**）：

```
环节产出 → 解析声明（没有 ⇒ 直接过，零成本）
        → 逐条走 Gate：enabled? 该 stage 授权? 三层配额? 预算?
        → 放行 ⇒ _web_search(...) ⇒ 结果**回喂**该环节（可选二次调用）
        → 一律写 web_trace（见 3.4）
```

★ **「不设限」在这里落地**：**框架不认识任何 stage 名单** —— 任何环节声明就接。
★ **「可控」也在这里**：所有声明都过同一个 Gate（授权 / 配额 / 预算）。
★ **向后兼容**：不声明 ⇒ 与今天逐字相同（加性）。

### 3.2 可控：在现有三层配额上加「预算 + 模式」

| 新键 | 语义 | 默认 |
|---|---|---|
| `web_search.mode` | `off`（= 今天的 false）/ `on_demand`（按需，见 3.1）/ `all`（所有授权环节都查一次） | `on_demand`（但**出厂 enabled 仍 false** ⇒ 总闸在 enabled） |
| `web_search.budget.per_run_queries` | 本次跑总查询次数上限（比 `per_run_total` 更前置的粗闸） | 30（= 现值，零差） |
| `web_search.budget.per_layer_queries` | 每层上限（跨 stage 汇总）—— 防某层吃光全跑配额 | 10 |
| `web_search.on_demand.max_per_call` | 单次声明最多几条查询（防一次要 20 条） | 3 |

★ 全部**默认零行为差**（值取自现有配置；出厂 enabled=false ⇒ 总闸仍关）。

### 3.3 运行中动态调整：**元层调度**（唯一实现）

**触发**：每层收尾（`_finalize_layer_common`）+ 每 N 圈。

**依据**（三类，都是**已有读数**，不新增计算）：

| 读哪 | 含义 | 调整方向 |
|---|---|---|
| `quant_readings.candidate_yield` | 候选产出率低（复述多） | ⇒ **放宽**该层联网（找新东西） |
| `quant_readings.restate_fidelity` | 重述漂移 | ⇒ 允许查「原始表述」佐证 |
| EML `web_policy`（见 3.5） | 该 stage 历史价值 | ⇒ 加权 |

**动作**（对 Gate 的**运行时**参数）：

```
gate.allow() 已经支持 disabled（失败降级）
  ⇒ 扩展成双向：relax(stage) / restrict(stage)
  ⇒ 只改**本次跑**的内存态（不改配置 ⇒ 红线「建议与执行分开」）
```

★ **留痕**：每次调整写 `web_trace`（谁调的、依据什么、调成什么）。

### 3.4 可追溯：**统一行为 trace**

**问题**：现在只有 `goal_trace` / `duty_trace` 两条**专用** trace ⇒ 「每个逻辑行为
都可追溯」无法满足。

**设计**：一条**通用 trace**，所有行为共用：

```python
view.trace(kind, **kw)   # kind: llm / web / judge / pool / stop / tune
```

| kind | 关键字段 |
|---|---|
| `llm` | `stage` / `calls` / `tokens` / `trunc` / `degraded` |
| `web` | `stage` / `queries` / `verdict`（放行/拒因）/ `n_hits` / `used_as` / `budget_left` |
| `judge` | `what` / `verdict` / `n` |
| `pool` | `op`（add/merge/drop） / `n` / `why` |
| `stop` | `reason` / `layer` / `source`（判据名） |
| `tune` | `who` / `param` / `old` / `new` / `why` |

★ **与现有两条 trace 的关系**：**并存**（不合并——它们各自被判据读）。
通用 trace 是**追加**的；将来可把两条专用 trace 改成「通用 trace 的视图」（另期）。

### 3.5 纳入自我学习：EML 新增 `web_policy` 条目

**记录**（每次跑完，从 `web_trace` 汇总）：

```json
{"kind": "web_policy", "q_feat": {"len": 42, "how": true, ...},
 "stage": "ing", "value": 0.67, "n_ev": 3,
 "note": "该题面特征下 ing 的联网命中被引用了 2/3 次"}
```

**学习**：EML 现有闸门 / 隔离 / 升级 / 遗忘机制**原样复用**（不新造一套）。

**应用**：跑开始时，EML 给出**初始 web 策略**（各 stage 的初始权重）⇒ 交给 3.3 的调度器。

### 3.6 供元层自我调度

元层读 `web_trace` + EML ⇒ 产出**下一跑策略建议**（写进建议文件，
**不自动改配置** —— 与 `autotune_*` 同规矩：**建议与执行分开**）。

## 四、分期实施（每期都可独立验收，且**默认零行为差**）

| 期 | 内容 | 判据 | 风险 |
|---|---|---|---|
| **P1 框架** | `===WEB-NEED===` 尾块协议 + 统一裁判器 + `web_trace` | 无声明 ⇒ 零调用；有声明 ⇒ 真走 Gate；trace 有记录 | 低（纯加性） |
| **P1b 预算** | 三个预算键（默认零差）+ Gate 支持 | 预算耗尽 ⇒ 拒且留痕 | 低 |
| **P2 关键环节接入** | 先接 **5 个高价值**：`_ing` / `_re_anchor` / `_expand_pair` / `_probe_*` / `_dual_judge`（**A 或 B 形态**） | 每环节：默认零调用 / 打开真调用 / **修行层不注入 prompt**（红线） | 中 |
| **P3 EML** | `web_policy` 条目 + 读侧 | 构造性证明「会学」（同 v1.23.31 的规格） | 中 |
| **P4 元层调度** | 运行时 `relax`/`restrict` + 依据读数 | 调整留痕；**不改配置** | 中 |
| **P5 追溯全面** | `view.trace` 通用化 + 各环节埋点 | 每个 kind 有产出；空值不表态 | 中 |

★ **顺序理由**：P1 是地基（协议 + 裁判 + trace 三件套），没有它后面都是散点；
P2 先接 5 个**最有价值**的（不是 29 个全接 —— 那会一次改 29 个 prompt，风险不可控）；
P3/P4/P5 依赖 P1 的 trace。

## 五、红线保护（逐条对应设计）

| 红线 | 本方案如何保护 |
|---|---|
| **输入是形状不是数据** | 修行层（entry `"0"`）仍然**不注入**任何联网结果进 prompt；其声明只进 pool + trace（本轮 `practice_term_calibration` 已按此实现） |
| **建议与执行分开** | 元层调度只改**本次跑的内存态**与**建议文件**，**绝不写配置** |
| **悬置不打分 / 未对齐合法** | 联网结果**不参与**任何"打分"；它只是**证据候选**（进引用表需过 `as_evidence` 门，已有） |
| **失败留痕** | 声明被拒（配额/预算/授权）**必须留痕**（`web_trace.verdict`），不许静默 |
| **入池前挡重复** | 复用现有 W# 编号 + 去重 |
| **零行为差** | 所有新键默认取现值；不声明 = 与今天逐字相同；两个 mock 判据分别钉「默认零调用」与「打开真调用」 |

## 七、待用户确认的设计选择（3 条）

1. **按需判定的归属**：由**环节自己**声明（本方案，最贴「按需」）？
   还是由**引擎规则**猜（不用改 prompt，但不是真"按需"）？
   ⇒ 本方案取前者（`===WEB-NEED===`），因为「按需」的"需"只有环节自己知道。
2. **P2 接哪 5 个环节**：本方案建议 `_ing`（对撞，最需要外部论据）/ `_re_anchor`（重述，
   需要原始表述）/ `_expand_pair`（展开，需要领域事实）/ `_dual_judge`（对偶判断，
   需要反例）/ `_probe_research`（研究探针）。
3. **元层调度的动作边界**：只调**配额松紧**（保守，本方案）还是也调**授权名单**
   （更激进，等于运行中开关某环节的联网）？

## 八、用户追问：「自我学习迭代是否可以参与自由调度」

### 8.1 答：**能，机制已经在，但参与面很窄 —— 且逮到「学而不做」**

#### 已参与（实测 `_eml_apply`）

| `action.key` | 作用面 | 状态 |
|---|---|---|
| `rounds_delta` | **每层圈数**（`rounds_plan[layer] += delta`） | ✓ 生效 |
| `duty_floor` | **职责下限**（守卫阈值 `self._duty_floor`） | ✓ 生效 |

⇒ **「圈数」与「守卫阈值」这两类调度，EML 已经在参与** ✓
（且遵守既有纪律：`mode=="on"` 才生效；出厂 `shadow` ⇒ 只记不用。）

#### ★ 逮到的问题：**3 类条目「学了不应用」**

| `action.key` | 出现次数 | 应用点 |
|---|---|---|
| `carve_first` | **1**（只在候选生成处） | ✗ **无** |
| `tri_advisory_only` | **1** | ✗ **无** |
| `note_cost_no_gain` | **1** | ✗ **无** |

⇒ 它们被**生成 → 过闸 → 存库 → 召回**，但 `_eml_apply` 里**没有对应分支**
⇒ **静默无效**。这正是本项目最忌讳的形态：**看起来在学，实际不作用**，
而且**没有任何判据会发现**（召回日志只说「用了几条」，不说「其中几条真的生效」）。

### 8.2 设计：EML → 调度的**完整接口**

**元DGTF 的调度面**（9 类）与 EML 参与现状：

| # | 调度面 | 谁在管 | EML 参与 |
|---|---|---|---|
| 1 | **每层圈数** | `rounds_plan` | ✓ `rounds_delta` |
| 2 | **守卫阈值** | `duty_floor` | ✓ |
| 3 | **并行模式**（serial/A~H） | `_decide_parallel_mode` / `auto_plan` | ✗ 可扩展 |
| 4 | **联网策略**（哪些 stage 开 / 配额松紧） | `_web_gate` | ✗ **本方案 3.5 要加** |
| 5 | **成本档**（quality/balanced/economy） | `cost_profile` | ✗ 可扩展 |
| ④ 停止阈值 | `stop.anytime_alpha` / `duty.tau` | ✗ 可扩展 |
| 7 | **思考档**（thinking / effort） | runtime 段 | ✗（**故意不碰**：它与"省钱"直接相关，交给 AutoTune 出建议） |
| 8 | **层序 / 路由** | `route` | ✗（结构固定，不该由记忆改） |
| 9 | **AutoTune 建议** | `autotune_*` | 已有（**只建议不落地**） |

**统一协议**（关键设计）：

```
EML 条目 = {cond, action:{key, ...}, readings}，召回后统一进 _eml_apply
  ⇒ ★ 规则：**每个 action.key 必须有 _eml_apply 分支，或在豁免表里显式登记并写原因**
```

⇒ 三件事：
1. **补齐**（3 类「学而不做」）：能接的接线（`carve_first` 可接到"职责不足时优先雕"），
   **不能接的**（`note_cost_no_gain` / `tri_advisory_only` 是**记录类**）⇒
   进**显式豁免表**并写「只记录、不应用」；
2. **扩展**（新增 key）：`web_policy`（联网）/ `parallel_mode_hint` / `cost_profile_hint`；
3. **判据**（一类）：`eml_candidates_from_result` 产出的**所有** `action.key`
   与 `_eml_apply` 的分支**两向对账** —— 生成得出但没分支、或分支没有生成源，都判红。

### 8.3 与「自由调度」的关系（一句话回答）

> **可以，而且是本来的设计**（`_eml_apply` 就是那个接口）。
> 现状是「**接口在、覆盖面窄（2/9）、还有 3 类空转**」。
> 本方案把它扩到「**9 类调度面都有明确的参与或豁免**」，
> 并用一条**两向对账判据**保证「**学了一定有人用**」。
>
> ★ 唯一不碰的是**答案本身** —— 红线「EML 只作用于调度与守卫阈值，不碰答案」保持不变。
