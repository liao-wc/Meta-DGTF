# 元DGTF 思考模式档位分配分析报告

**日期**：2026-10-02
**版本**：fix-112
**范围**：`元DGTF-V1.21.61.py` 全部 34 个 LLM 调用点，归并为 26 个环节
**结论**：按「这一步是不是多步推理」分层，需要开的开、不需要的关

---

## 一、摘要

迁移到显式模型 ID 后，`default_model` 与 `reasoner_model` 同名（都是
`deepseek-flash`），「开不开思考」变成一个独立的请求参数。原配置里只有
2 个环节开思考（`_ing` 对撞、`_manifest` 显形），而且这两个都是**生成型**；
所有判定型环节全关。这个分配是历史遗留（老别名 `deepseek-reasoner` 只在
两处用），不是测量结果。

本报告给出逐环节的档位分配，判据是：

> **不是「生成长文本才需要思考」，是「这一步是不是多步推理」。**

依据实测（§7.19）：在有区分度的题上，非思考 0/4、思考三档全 4/4——
思考模式的收益在**多步推理**上出现，与「输出长短」无关。

**落地结果**：

| 档位 | 环节数 | 说明 |
|---|---|---|
| ✅ 开思考 | 8 | `auto_plan`、`adjudicate_sub_tristate`、`dual_judge`、`assess_decidability`、`assess_decidability_from_pool_view`、`re_evaluate_pool` + 历史已开的 `ing`/`manifest` |
| ⏸ 关思考 | 15 | 简单映射 / 结构化罗列 / 输出本就短 |

> `dual_judge` / `assess_decidability` 是**先验开启**（多步推理 + 直接进 X/Y），
> 不是已实测验证——专项对照批用真实 X/Y 判据验证「开 vs 关」仍是待办。

---

## 二、判据

每个环节按四条打分，综合决定开不开：

1. **认知负荷**：这一步是「多步推理」（要权衡、比较、给理由）还是「单步
   映射」（看输入直接产出结构化结果）？
2. **判定质量的下游影响**：结果是否直接进入 X/Y（已答子问题/可判定分母），
   错了会不会污染整个质量口径？
3. **调用频次**：每跑 1 次（低频，成本可忽略）还是每层每圈都调（高频，
   开思考的成本要乘几十次）？
4. **输出形态**：JSON（思考模式下 `response_format` 不生效，需额外容错）
   还是自由文本（无此风险）？

**开思考的必要条件**：①多步推理 且 ②下游影响大。**充分性**还要看 ③频次
（高频先测成本再开）和 ④JSON 风险（已实测排除，见第五节）。

## 四、为什么「高频」环节不能直接开

`dual_judge` 和 `assess_decidability` 是**先验最该开**的两个（多步推理 +
直接决定 X/Y），但它们是**圈级高频**调用。实测思考档的 output 是中位 6308
token，非思考 349 token——**约 18 倍**。

按一次 run 约 187 calls、其中判定类高频环节占 20~30 次的粗估，开这几个
会带来：

- 每 run 约 +30 万~50 万 output token
- 24 run 的 mx batch01 整批约 +¥30~50（flash off-peak 输出价 $0.60/1M）
- 余额已充到 ¥156，**够跑**，但仍是主要成本来源

**已按先验开启**（用户拍板），但**必须**在专项对照批里用实测 X/Y 判据
验证「开 vs 关」的质量差——先验开启不等于已验证，这一步不能省。

## 五、硬约束已排除：思考模式下的 JSON 仍可靠

判定/规划类 18 个调用点 **100% 是 JSON 输出**，而生产代码在思考模式下
**不发 `response_format`**（`LLM.call`），JSON 只能靠 prompt 约束。这是
「给判定开思考」的最大技术风险。用生产真实 schema（`_dual_judge` 嵌套数组
+ 6 字段 + 理由）实测：

| 档位 | json.loads 可解析 | 结构完整 | output 中位 |
|---|---|---|---|
| 非思考（+response_format） | 5/5 | 5/5 | 349 |
| 思考（prompt-only） | 5/5 | 5/5 | 6308 |

→ 思考模式 JSON **5/5 可靠**，风险排除。可复现：`_json_thinking_probe.py`
（支持 `PROBE_MODEL` / `PROBE_REPS` 环境变量）。

⚠️ 该数据测于 `deepseek-v4-pro`（当时 flash 故障）。机制结论跨模型可迁移；
6308 这个定量数需 flash 重测确认。

## 六、成本与风险

1. **effort 设 `low`**：理由已从「三档打平选最便宜」**修正为「成本最小化是
   唯一有把握的理由」**。flash 重测（06:24）这批 8 题**四档全打平、无区分度**
   —— flash 非思考模式在这批算术题上就全对，测不出 low/high/max 的差别。
   这不是「三档等价」的复现，是「题太简单测不动」。档位差异需更难的题重测；
   在此之前保持 low 是稳妥的（成本最低，且无证据表明更贵的档位更好）。
2. **档位分配的可回滚性**：全部在 `dgtf_config.yaml` 的 `thinking.stages`，
   逐环节可改；优先级「显式 thinking > stage > default」。
3. **预注册批不受影响**：`_auto_pipeline.py` 跑 mx batch01 时固定
   `V60_STAGE_THINKING=off`，24 跑在旧档位下完成，与已完成那跑可比。
   新档位留待该批之后的专项验证。
