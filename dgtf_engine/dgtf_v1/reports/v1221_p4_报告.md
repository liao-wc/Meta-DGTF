## 三、★ 任务书指定的口径在 OFF 臂**不可用**（本档最重要的发现）

任务书 Step P4.3 的口径是产物 md 里这一行：

```
**三态多票**：high N / medium N / low N（共 N 条）　一致率 X%
```

实测六份产物原文：

| 跑 | 该行 | calls |
|---|---|---|
| ON1 | `high 5 / medium 0 / low 0（共 5 条）　一致率 100%` | 45 |
| ON2 | `high 4 / medium 1 / low 0（共 5 条）　一致率 100%` | 46 |
| ON3 | `high 5 / medium 0 / low 0（共 5 条）　一致率 100%` | 46 |
| OFF1 | `high 0 / medium 0 / low 0（共 6 条）　一致率 0%　⚠️ unstable（＜50%）` | 44 |
| OFF2 | `high 0 / medium 0 / low 0（共 5 条）　一致率 0%　⚠️ unstable（＜50%）` | 44 |
| OFF3 | `high 0 / medium 0 / low 0（共 5 条）　一致率 0%　⚠️ unstable（＜50%）` | 45 |

初看是「ON 100% vs OFF 0%，多票更好 +100%」。**但这个 0% 是假的。**

那一行读的是每条子问题的 `stability` 字段，而 **`stability` 只有多票路径
（`_adjudicate_sub_tristate_multi`）才写**。OFF 走的是单票路径
（`_adjudicate_sub_tristate`），子问题里**连 `stability` 这个键都没有**：

```
ON1  subs 5 | stability ["high","high","high","high","high"] | 有该键 True
ON2  subs 5 | stability ["high","high","high","high","medium"] | 有该键 True
ON3  subs 5 | stability ["high","high","high","high","high"] | 有该键 True
OFF1 subs 6 | stability [null,null,null,null,null,null] | 有该键 False
OFF2 subs 5 | stability [null,null,null,null,null] | 有该键 False
OFF3 subs 5 | stability [null,null,null,null,null] | 有该键 False
```

键都没有 → `_hi = _me = 0` → 引擎照 `(0+0)/n` 印出「一致率 0%」，
还顺手加了个 `⚠️ unstable（＜50%）` 的告警。**这是「没算」，不是「算出来是 0」。**

★ 这是**先前就有**的渲染问题（v1.22.0 的阶段 2 头部渲染），不是本档引入的；
P4 的 ON/OFF 设计只是第一次让它**显形**。本档**不改**它（不在 P4 授权范围），
只把它写清楚，并因此**拒绝**用这个口径下结论 —— 否则就会得出
「多票更好 +100%」这种**建立在一个不存在的读数上**的结论。

汇总脚本已把它标出来（`_v1221_p4_consistency.json` 的 `md_metric.usable = false`
与 `alerts`），验收里也加了 `P4.2.c` 要求报告必须写明这一点。

## 四、公平口径：`tri_state` 一致率（两臂都可得）

打包里另有一个两臂都写的字段：`tri_state = [agree, total]`。

| 跑 | `tri_state` | 一致率 |
|---|---|---|
| ON1 | [4, 5] | 80% |
| ON2 | [4, 5] | 80% |
| ON3 | [4, 5] | 80% |
| OFF1 | [3, 6] | 50% |
| OFF2 | [4, 5] | 80% |
| OFF3 | [3, 5] | 60% |

**去掉了漂移的 OFF1（6 条子问题，比 ON 多 1 条）后仍是 [4,5] 与 [3,5]。**

| 统计 | ON | OFF |
|---|---|---|
| 平均 | **80.0%** | **63.3%** |
| 组内极差 | **0.0%**（80/80/80） | **30.0%**（50/80/60） |
| 组间差 | — | **+16.7%** |

### P4.4 判定（按任务书自己的两向规则）

```
组间差 +16.7%  → 落在「≥ +10% → 多票更好」这一档
但 OFF 组内极差 30.0% ≥ 组间差 16.7%
→ 按 P4.4「若组内极差 ≥ 组间差，则**无结论**」
```

⇒ **无结论。** 本项目的纪律就是这条：**组内抖动比组间差还大的时候，
差值读不出来**。3 次重复里有 1 次是 50%、1 次 80% —— 这个散布水平下，
「ON 比 OFF 高 16.7%」和「掷骰子」暂时分不开。

★ 若要真出结论，需要先把 OFF 的组内极差压下去：**增加重复次数**
（同条件 ≥3 是下限，不是够了）或**固定采样温度**。本档只跑 3 次（任务书要求），
如实报「无结论」。

## 六、遗留与下一版候选

1. **`stability` 只由多票路径写** → 单票路径下头部那行「一致率 0% ⚠️ unstable」
   是**假告警**。下一版正路（三选一）：
   ① 单票路径也写 `stability`（单票的「稳定」可以定义为「与拆解原标签一致」→ high，否则 low）；
   ② 头部渲染在 `stability` 键缺失时**不印那一行**，改印「（多票未开启，本行不适用）」；
   ③ 统一成 `tri_state` 一条口径，两条路径都写。
   ★ 本版**不动**：改头部渲染 = 改产物格式，改 `stability` 写入 = 改行为，都不在 P4 授权内。
2. **OFF 组内极差 30%** 太大 → 需要 ≥3 次以上的重复（或降温）才能谈「多票是否更好」。
3. **`tri_state` 与 `stability` 是两个不同的量**：前者是「判决 vs 拆解原标签」的一致，
   后者是「三票之间」的一致。本报告用的公平口径是前者；若下一版要谈「多票对**判定稳定性**
   的贡献」，正确做法是让单票路径也产出「同一把尺子」的量（即上方 ①）。
