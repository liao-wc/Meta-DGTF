# 元 DGTF v1.21.67 · 交付报告

- **版本**：`元DGTF-V1.21.67.py`（17298 行 / 纯 CRLF / `__version__ = "1.21.67"`）
- **上一版**：`元DGTF-V1.21.66.py`
- **本轮主题**：**完整性** —— ① 每次运行的真跑日志不得有遗漏、要显示所有内容；
  ② 保存的产物 md 要包含所有内容，**显示的未显示的都要有**。
- **一句话结论**：日志侧补齐了 3 类原本根本不进日志的内容（引擎 `logger.info`
  被整条丢弃、`warning/error` 只到 stderr、其余 stderr 输出）；产物侧补齐了
  **925 条叶子路径中 815 条正文里找不到名字**的字段 —— 由「机械全量附录」兜底。

## 一、要求与核对口径

用户要求（原文）：

> 检查每次运行输出的日志和 md 内容是否有遗漏，让日志显示所有内容并完整输出，
> 最后输出保存的 md 文件内容要包括所有内容，显示的未显示的都要有。

拆成两条可验证的口径：

| 口径 | 怎么算「没有遗漏」 |
|---|---|
| 日志 | stdout / stderr / logging **三类输出都进同一份日志**，且首尾有哨兵、末尾有**逐类计数**的完整性行 |
| 产物 md | packed 的**每一条叶子路径**都能在 md 里找到 —— 不是「重要的都渲染了」，而是**一条不落** |

## 四、[A] 引擎侧：产物 md 追加「附录 · 全量字段（packed 原文）」

**做法**：`save_result` 正文写完后，把 packed **原样 JSON** 追加进同一份 md，
并给一行完整性统计：

```
## 附录 · 全量字段（packed 原文）
<sub>本段是**机械全量**输出：正文各节是 packed 的可读视图，凡正文省略的、
或压根没有渲染点的字段（含以 `_` 开头的内部量），**以本段为准**。</sub>

- 叶子路径 925 条；正文里**找不到字段名**的 815 条（按「字段名是否在正文
  出现」粗算，不是精确覆盖判定）
- JSON 44576 字符 / 1432 行

```json
{ … }
```
```

**★ 为什么用「机械全量」而不是「再挑几个字段渲染」**：挑字段等于又维护一张
「该渲染什么」的清单 —— 新增字段会**再次静默漏掉**，本项目的「无渲染点」事故
就是这么来的。机械全量没有这个失效模式。

**失败也要留痕**：序列化失败时往产物里写一句「❌ 序列化失败，本段缺失⇒ 这一份
产物不完整」——否则产物会看起来「完整」而其实缺了一段。

## 五、[B] 工具侧：`_run_verif.py` 日志收全

| 措施 | 说明 |
|---|---|
| 分流捕获 + 计数 | `_Cap(fh, tag, counter)` 包住 stdout 与 stderr，各自累计行数 |
| logging 进同一日志 | `_CountHandler` 挂在根 logger（INFO 起），按级别计数 |
| wrapper 自身消息进日志 | banner / question / module / min_rounds 覆盖 / counts / dispatch / views / artifacts 全部 `emit`（同时回显控制台） |
| 首尾哨兵 | `############ LOG BEGIN/END <iso> ############` |
| 完整性统计行 | `[completeness] stdout 行 N｜stderr 行 N｜logging X=N…｜异常：有/无` |
| 降噪白名单 | openai / httpx / httpcore / urllib3 / asyncio / jieba / charset_normalizer / filelock → WARNING。**否则 DEBUG 会把请求体（含 key）倒进日志** |
| packed 全量侧车 | `verif_<tag>.full.json`（与产物附录同源，便于工具链读取） |
| `_Cap` 补齐属性 | `encoding / errors / mode / buffer` —— 引擎与第三方库会读 `sys.stdout.encoding`，缺属性会在深处抛 AttributeError，把「收全」变成新故障源 |

## 八、已知遗留与下一轮建议

1. **产物体积**：md 随 packed 线性增长（单层 2 圈已 59K 字符；四层 5 圈预计
   300K+）。要不要给全量附录加体积阈值 / 拆侧车，属格式决策 —— 现在
   **完整性优先**，等实际需要再定。
2. **附录是 JSON，人读不友好**：将来若要「人读版全量」，应**另开一节**，
   不要动附录的机械性（机械性正是它的价值）。
3. **`logger.info` 只有 6 处**：本轮只保证「已有记录不丢」，没有新增日志点。
   若某类事故仍难复现，应补 `logger` 调用而不是靠 print。

## 九、经验教训

1. **「没渲染点」与「渲染了但值为 0」是同一类事故的两面。**
   v1.21.66 用「覆盖计数」治了后者，这一轮用「机械全量附录」治前者。
   共同解法：**别维护「该渲染什么」的清单，让结构自己说话**
   （覆盖计数 = 无条件写；全量附录 = 整包落盘）。
2. **日志收全不是「多写几个 print」，而是要能证明。**
   所以给 stdout / stderr / logging 各自计数，并**用单测覆盖最容易漏的那几类流**
   —— 干净跑里引擎不吐 warning，光靠真跑验不出来。
3. **改格式之后要跑下游回归**。附录往产物里灌了 44K 字符 JSON，很可能污染
   按正则抽 `revisit_condition` 的回归脚本；实测语料仅 +7，才敢说没污染。
