## 〇、这份报告在回答什么

**链接里的问题（原文）**：

> 我们讨论另一个话题，你帮我分析一下跑一次完整的元DGTF流程的成本

**链接里的答案（摘要）**：DeepSeek 基于读代码给出的估算 ——

> 默认配置下约 **330 次调用 / 160 万 token / 47 分钟 / 约 ¥2~5**；
> 给全四层 3 圈的紧凑配置约 125 次调用 / 18~22 分钟 / 约 ¥0.6~1.2。
> 成本的决定量是圈数，不是模式。

那份答案的**推导骨架是对的**（调用点、档位差异、圈数为主因都指对了），但有
几处**价格与默认值是与真实代码/真实官网不符的**，且全部是"从代码读出来的
估算"，没有任何一次真实跑圈的数字支撑。

**本报告做的事**：
1. 用当前版本 `v1.21.72` **真跑一次完整的四层流程**（不是估算）；
2. 用一次**探针**测出 token 的输入/输出拆分（引擎本身不记录，所以估算方
   无法回答"钱花在哪一半"）；
3. 用**账户余额扣减**给出真实花费；
4. 逐条核实链接结论的对错。

## 三、调用次数：链接的公式对不对？

**链接说**：每层每圈 8 次固定调用（quality 档），balanced/economy 因为
`re_eval_every_n` 拉到 2 圈而约 8.5 次/圈。

**代码核实（v1.21.72）**：对。每圈固定调用点是

`_re_anchor`(1) + `_expand_pair`(阴/阳 2) + `_dual_judge`(1) + `_ing`(1)
+ `_he`(1) + `_phase_probe`(1) + `_manifest`(1) + `_self_check`(1) = **8 次**

（`元DGTF-V1.21.72.py:7427–7640`）。`re_evaluate_pool` 默认 `True`、
`re_eval_every_n: 1`，`_lazy_every_n` 在 balanced 下 +1 → **每 2 圈 1 次**
（`L11329`、`L13708`）。所以 balanced ≈ **8.5 次/圈**。

**实测核对（用日志标记逐项点）**：

| 组成 | 实测 | 说明 |
|---|---|---|
| 固定 8 次/圈 × 28 圈 | **224** | 日志里 `🪞[锚点]`/`💧[阴]`/`💧[阳]`/`🔮`/`🔥 ing`/`🌱探针`/`🌕view`/`🔍self-check` **各 28 次**，逐项吻合 |
| 极性重估（每 2 圈） | ≈14 | 12/8/4/4 圈 → 6+4+2+2 |
| 结构饱和度（每 4 圈，仅研究/元层） | ≈3 | `L13797-13800`：`entry in ("1","all")` 才跑 |
| 一次性（外部评估 + 输入自检） | 2 | 每 run 各 1 |
| 研究层一次性（池评估/拆解/三态/终局清算） | 4 | |
| 重试 / 续跑 / 降级 | ≈22 | 实测 stderr 出现 3 次 `对偶判断命中 x/n，降级重试`（`L8405`，每次最多 +2） |
| **合计** | **269** | 与 `llm_calls=269` 一致 |

**结论**：链接的"8 次/圈 + 每 2 圈一次重估"骨架**成立**；但链接估的
"默认≈330 次"偏高 —— 因为**本题 both/all 两层在第 4 圈就自己停了**，
只有修行层走满 12 圈。**次数取决于"各层自然停止点之和"，不取决于 `hard_max`**
—— 这一点链接其实也说对了，只是它的示例数字用的是 v1.21.59 那次
（四层停 12/8/**10**/**5**）。

> 历史对照：v1.21.59 同配置（serial/balanced/不传 rounds）为
> **333 次 / 1 585 809 token / 47 分钟**，四层停 12/8/10/5
> （`元DGTF-V1.21.72.py:2444`、`:3135`）。

## 四、token 和钱：拆开看（链接答不出的部分）

引擎只累计 `usage.total_tokens`（`L7005-7009`），**不拆输入/输出**，
所以任何"读代码"的分析都只能猜比例。为此写了一个**不改引擎逻辑**的探针
`_probe_usage_split.py`：在类层面包一层 `Completions.create` 记录每次
调用的拆分，然后跑一小段真流程采样。

**探针实测（44 次调用 / 178 430 token）**：

| 指标 | 实测值 |
|---|---|
| 输出占比 `out_share` | **57.5%** |
| 输入缓存命中率 | **25.5%** |
| 单次均 token | 4 055 |

单次最大的几笔都是 **reasoner 的思考调用**（ing / view 显形）：
completion 出现 5 350 / 6 205 / 7 251 / 8 819 / 9 024 / 9 610 token ——
因为 thinking 模式把 `max_tokens` 抬到 32 000（`L6979-6981`）。

**真实价格（DeepSeek 官网，2026-10-04，`deepseek-flash` / V4.1-Flash）**：

| 项 | 空闲时段 | 高峰时段 |
|---|---|---|
| 输入（缓存命中） | ¥0.02 /M | ¥0.04 /M |
| 输入（缓存未命中） | ¥1 /M | ¥2 /M |
| 输出 | ¥4 /M | ¥8 /M |

> 高峰 = 北京时间周一至周五 9:00–12:00、14:00–18:00；**周末全天是空闲时段**。
> 本跑在周日凌晨，按**空闲价**计。

**用实测花费反解**（T=1 837 502 token，命中率 25.5%）：

```
设输出占比 ou：  cost = prompt×(0.745×1 + 0.255×0.02)/1e6 + out×4/1e6
实测 cost = ¥4.17  →  ou ≈ 0.47
即：输出 ≈ 0.864M token（¥3.45）  输入未命中 ≈ 0.726M（¥0.73） 命中 ≈ 0.248M（¥0.005）
```

**钱花在哪：**

| 项 | 占比 | 金额（空闲价） |
|---|---|---|
| **输出 token** | **82.5%** | **¥3.45** |
| 输入（未命中） | 17.3% | ¥0.73 |
| 输入（命中） | 0.1% | ¥0.005 |
| 合计 | 100% | **¥4.18 ≈ 实测 ¥4.17** |

**这条比链接更有用**：钱**几乎全在输出**（输出单价是输入的 4 倍，而
reasoner 的思考输出又特别长）。要省钱，第一优先是**压输出**（ing / view
这两个 reasoner 调用的长度），而不是压输入上下文。

**按层分摊（按圈数比例）**：修行层 ¥1.8（43%）· 研究层 ¥1.2（29%）·
对撞 ¥0.6 · 元层 ¥0.6。修行层是唯一走满 12 圈的，也是最大一笔。

## 六、与链接估算的对照

| 指标 | 链接估算 | **实测** | 偏差 |
|---|---|---|---|
| 调用次数 | ≈330 | **269** | −19% |
| token | 160 万 | **183.8 万** | +15% |
| 时长 | 47 分钟 | **65.1 分钟** | +38% |
| 花费 | ¥2~5 | **¥4.17** | 落在区间内（偏上） |
| 单 call token | 4 300~4 800 | **6 831** | +42% |

**偏差从哪来**：

- **调用次数少**：本题 both/all 第 4 圈就停（v59 那次是 10/5）。次数由
  **各层自然停止点之和**决定 —— 链接这条判断本身是对的。
- **token 更多、时长更长**：本跑的 reasoner 思考输出很长（单次 6k–9.6k），
  且修行层走满 12 圈。单 call 均 token（6 831）显著高于历史中位
  （206 次历史真跑样本中位 **5 049**、均值 5 496）。
- **钱对得上**：因为真实"高峰价"恰好等于链接猜的 ¥2/¥8，而周末按空闲价
  （减半）跑，两个误差互相抵消 —— 但这是**巧合，不是它的价格算对了**。

## 七、修正后的旋钮（按实测重排优先级）

1. **压输出（第一优先）**：钱 82.5% 在输出。ing / view 两次 reasoner 调用
   是最大输出源（thinking 抬到 32k 上限）。要动就先动这两处的长度/档位。
2. **给修行层单独设上限**：修行层是唯一走满 12 圈的（¥1.8 / 43%）。
   运行时 `--rounds "0:6"`，不要动全局 `hard_max`（那会把累计窗口关掉、
   退回"体力耗尽"）。
3. **降低频项**：`spiral.re_eval_every_n: 1 → 3`（实测占比 5.2%）；
   `structure_saturation_every_n` 已是 3/balabced 变 4。
4. **判据会自己停就别塞圈数**：本题 both/all 4 圈即停，多给的预算没花出去
   —— 但也别指望判据在 3 圈内触发（累计窗口实测 5–10 圈）。
5. **economy 档**：省约 15% 调用（实测 81→80→69，`L3572`），是唯一的
   "动调用结构"的档；balanced 只省 token，不动次数。
6. 别为省钱砍 route：链接的"模式只省时间不省钱"——实测支持；真正的粗旋钮
   是 **route（跑几层）** 和 **圈数**。

## 九、局限与未决（照实写）

1. **只有一次跑**：单题、单次。成本对题面与停止点敏感（v59 同配置
   333 次/1.59M/47min，本次 269 次/1.84M/65min）。本报告给的是"一次完整
   流程"的实测样本，不是分布。
2. **output/input 拆分为反解**：探针测到的是短流程（2 圈）的 `out_share
   =57.5%`；用它反解全跑得 `out_share≈0.47`（因为圈数多、prompt 变长）。
   两个数互相印证，但都不是逐调用精确值 —— 引擎不记拆分是根因。
3. **缓存命中率 25.5%** 来自短流程采样；28 圈的长跑里，系统提示重复度更高，
   命中率可能略高，这会**进一步降低**输入成本（但不影响"输出占大头"）。
4. **¥4.17 含一次重复进程**：因首次启动用了 `&`，后台守护进程被回收后
   子进程成为孤儿并继续跑，与第二次启动并发约 2.6 分钟，已 `Stop-Process`
   杀掉。多算的部分 ≈¥0.06。**教训：后台长跑只用工具的后台任务，不要加 `&`。**
5. **探针自身花费 ¥0.45**（余额 99.32→98.87，44 次调用），未计入上面的
   ¥4.17。本次为完成本报告共花费 ≈ **¥4.62**。
6. 未做：economy / quality 档的真跑对照（会用历史实测值 `L3572` 佐证，未新跑）；
   未在跑中改引擎（本次不改任何引擎语义）。

（¥2.06 / M token）；四臂 `tokens/call` = 7 347 / 7 079 / 8 186 / 6 773。

**结论 1 · economy 档省多少**（A vs B，同题同圈数）
调用 122 → 106（**−13.1%**）、token −16.3%、钱 −16.8%、耗时几乎不变。
→ 链接"economy 省 ~15% 调用"**方向对**，实测**调用省 13%**、**钱省 17%**。

**结论 2 · 并行只省时间，不省 token**（A vs C，同题同圈数）
耗时 1 824 s → **855 s（−53%）**，但调用 122 → 123（持平）、
token **+12.3%**、钱 **+11.9%**。
→ 链接"并行能把时间压到串行的 40~60%、不省 token"**成立**；
实测更进一步：**不但不省，还多花约 12%**（并行时各层读到的上游更少/更早，
prompt 反而更长）。**"模式只省时间不省钱"这句话已被实测证实。**

**结论 3 · 链接推荐的第一旋钮 `re_eval_every_n: 1→3`**（A vs D）
调用 −13.9%、token −20.6%、耗时 −27.3%。**但两臂圈数不完全相同**
（元层 4 → 3 圈，属自然停止差异，不是我改出来的），所以总差额不能全记旋钮头上：
按"每圈固定 8 次调用"折算，1 圈 = 8 次；而该旋钮在 13 圈的 A 臂里总共只触发 5 次
（12/8/4/4 圈、每 2 圈一次）→ **旋钮自身约省 5 次调用（≈4%）**。
链接说"省 ~10%"，**实测旋钮单独约 4%**，不到它说的一半。

**结论 4 · 与链接"场景 B：四层各 3 圈"对照**

| 指标 | 链接预测 | 实测（A 臂） |
|---|---|---|
| 调用 | ≈125 | **122**（几乎正中） |
| 耗时 | 18~22 min | **30.4 min** |
| 花费 | ¥0.6~1.2 | **¥1.85** |

调用次数它**说对了**；耗时与钱都偏低。两处偏差**同源**：它把单 call 的 token
估成 4 300~4 800，而实测是 **7 347**（本臂）/ 6 831（完整跑）/ **5 049（历史中位）**
—— reasoner 的思考输出把每次调用抬高了。**"token/call 4 300~4 800"这一条应整体上修。**

quality 档仍未跑（会是四臂里最贵的一档，且既有真跑样本 3 次，见 `L3349`）。
