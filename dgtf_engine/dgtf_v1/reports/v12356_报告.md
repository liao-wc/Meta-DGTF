## 二、问题：续跑把前面的钱抹掉了

A/B 真跑时我盯着快照，发现数字对不上：

| | 实际 | 快照里写的 |
|---|---:|---:|
| A 臂 `V1255A` | **230 calls / 1,710,346 tokens** | **97 calls / 928,547 tokens** |

原因：快照的计数取自 `self.llm.total_calls`，那是**按实例**的计数器。续跑会新建
`MetaDGTF` ⇒ `LLM` 也是新的 ⇒ 计数器归零。于是**第二个窗口的快照只记本窗口**，
前面那个窗口的钱在快照里查不到。

这直接打穿 v1.23.50 立命的那句话 —— **「被杀跑次也能结算成本」**。这次我是靠
另建外部账本（`*.spend.json` 按窗口累加）才把总账算对的；但那是我在脚本里打的补丁，
**引擎本身仍然会给出错数**。

> 一句话：**「硬上限 / 成本结算」这类口径必须跟 `run_id` 走，不能跟实例走。**

## 三、修法

1. `load_resume_snapshot` 把快照里的 `llm_calls` / `llm_tokens` 一起返回。
2. `run()` 拿到续跑快照时记进 `self._ck_base`（跨窗口基线），并把基线打进日志：
   `💰 续跑记账基线：已花 N calls / M tokens`。
3. `_ckpt_snapshot` 落盘时：

```python
_base = getattr(engine, "_ck_base", None) or {}
_w_calls = int(getattr(_llm, "total_calls", 0) or 0)
_acct = {"llm_calls": int(_base.get("calls") or 0) + _w_calls,   # 累计：结算用
         "window_calls": _w_calls,                                 # 本窗口：分析用
         ...}
```

**两个口径都留**，因为它们回答不同问题：结算要累计（"这条 run_id 一共烧了多少"），
分析要窗口（"这一窗干了多少活"）。只留一个，另一种问题就答不了。

不传 `resume_ckpt` ⇒ `_ck_base` 全 0 ⇒ 数值与旧版**逐字相同**。

## 四、影响面与判据更新

| 面 | 影响 |
|---|---|
| 不续跑 | 逐字不变（基线 0） |
| 续跑 | 快照 `llm_calls` 变累计；新增 `window_calls` / `window_tokens` |
| 被强杀（`interrupted`） | 下次续跑也从快照带基线 ⇒ 真能结算 |
| 外部账本（`*.spend.json`） | 仍可并行使用，两者应当对得上 |

### 判据更新（登记式）

`check_v12350_resume` 里有一条**静态字面量**断言：

```python
'"llm_calls": int(getattr(_llm, "total_calls", 0) or 0),'
```

它把"快照带记账"钉在**一行源码的字面量**上 —— 本版改实现就失配 ⇒ **假红**。
改成新字面量（`int(_base.get("calls") or 0) + _w_calls`）。这条 check 本来就有
行为级断言（快照 `llm_calls > 0` / `llm_tokens > 0`），静态那条只是顺带指纹。

> 这又是一次「锚钉在会变的东西上」。**教训不变**：能测行为就别测字面量；
> 非要测字面量，就准备好它随实现更新。

## 七、经验教训

1. **「硬上限 / 成本结算」必须跟 `run_id` 走，不能跟实例走。** 实例级计数器在
   "会重启"的流程里等于假的。
2. **两个口径就该留两个字段。** 累计 vs 窗口不是冗余，是两个不同问题；
   合并成一个，总有一种问题答不了。
3. **「0 判红」有两种含义**：判据没牙（真问题）或变异体没插进去（工具问题）。
   不看锚点命中数就下结论，会把工具问题当成判据问题去"修"。
