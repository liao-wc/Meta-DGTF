### 1.2 复核中被推翻 / 需要修正的外部说法（必须记下来）

1. **F3 的「`_build_inp_duel` 同样处理」不成立**。
   `_build_inp_duel` 的 `upstream_pools` 是**固定的** `[self.pools["0"],
   self.pools["1"]]`，与上游 view 的 `entry` 无关 → 没有 KeyError 风险。
   实测亦无异常。**本版不动它。**
2. **F4 的「`load_config("不存在.yaml")` 应打印警告」与代码意图不符**。
   不存在的路径**静默回落默认配置**是既有语义（`if not (...exists())`），
   改前的实测就是 `missing_yaml 警告=False`。真正该修的是**空路径**误报。
   本版只修空路径，**不改"不存在即静默"这条语义**。
3. **F11 的「`outputs/diagnostic_position_*.log` 会双倍增长」没有观测到**。
   两次观测里**两个站点从未同时命中**：
   - mock 四层跑（候选 position 交替）→ `in_round=0 / in_finalize=4`；
   - V71S 真跑 → 只产出 **1 个**诊断文件（`entry=all, round=2`，来自圈内站点），
     收尾站点的抑制日志 **0 条**。
   同时发现一个**外部没提的**事实：文件名的**秒级时间戳会撞名**
   （同一秒内两次写入互相覆盖），所以"数文件个数"本身不是可靠判据 ——
   本版判据改用 **dump 尝试次数**。
   ⚠️ 但 F11 与 F1 有**交互**：F1 让单圈层也进收尾，若不同时加这个开关，
   一次单圈四层跑会**新增 4 份**收尾诊断。所以 F11 的价值是**预防性的**，
   本版保留。
4. **#6（`stop_reasons` 来源问题）外部已自行撤回**，本版不处理。

## 二、逐项改动（F1~F11）

> 通用纪律（任务书给的 8 条）逐条遵守：先量后改 / 用脚本改文件 / 加性优先 /
> 失败必须留痕 / 不改判据语义值 / docstring 不写单反斜杠 / 冒烟带负对照 /
> 不做的写清为什么。

### P0 · F1 单圈层跳过全部收尾逻辑

- **位置**：`_run_layer` 的收尾调用点（serial 通道）、`_b_finalize_layer` 的
  守卫（B/C/D-H 通道）。
- **根因**：两处各有一道 `> 1` 门 —— serial 是 `if view is not None and
  rounds_n > 1:`，B/C/D-H 是 `if state["total_rounds"] <= 1: return`。
  `rounds = 1` 的层于是拿到一个**没有** `roles_run / rounds_cap / round_log /
  stop_reason` 的 view，**合并后二次去重与质量检查也全不执行**。
  这是本项目「同一条逻辑两条通道各写一份」的第 7 次（两处**同时**改）。
- **做法**：serial 侧改成 `if view is not None:`；B/C/D-H 侧删掉早返回。
  `_finalize_layer_common` 的 docstring 里「调用方只在 `rounds_n > 1` 时才
  进入」已经不成立，同步改写（**self 记忆仍然不放进该函数**，双写风险不变）。
- **验证**：见 §四（探针 [A] + 出口 E2E + 两次真跑）。
- **副作用**：单圈层的日志会多出 `dump_final` 的「收尾留痕」段、
  产物会多出 round_log 表与 `**螺旋停止**` 行 —— 这正是欠的账。

### P0 · F2 `main()` 里 `save_result` 没有兜底

- **位置**：`main()` 末尾。
- **根因**：`_interactive_run` 早就有 `try/except`（打印「保存失败」继续），
  `main()` 却裸调 → 任何 IO 失败**整轮结果丢掉**，终端只剩 traceback，
  且没有可判的退出码。
- **做法**：包 `try/except`，失败时打印原因 + 一句「没有落盘」+ `sys.exit(1)`。
  成功路径不变。

### P1 · F3 `_build_inp_meta` 的 KeyError 隐患

- **做法**：**配对过滤** —— `entry` 不在 `self.pools` 里的上游 view **与其池
  一起剔除**，绝不静默换成默认池（换池等于让元层读错形状还不自知）。
- **留痕三处**：`logger.warning` / 实例字段 `_build_inp_dropped` / verbose 终端。
- **注**：`_build_inp_duel` 不处理（复核不成立，见 §一.2.1）。

### P1 · F4 `load_config("")` 误报

- **做法**：`if not path or not (HAS_YAML and Path(path).exists()):`。
- **反向锁**：真坏的 yaml 仍必须报「配置文件解析失败」（冒烟两个方向都测）。

### P1 · F5 C / D-H 早退时 `dispatch` 为空

- **做法**：两处早退补 `_dispatch_for_pack(...)`，模式名取**实际变量**
  （C 处 `"C"`，D-H 处参数 `mode`），不硬编码；顺带带上 `_warmup_rounds`。

### P1 · F6 单次运行跑两次外部可判定性评估

- **做法**：`__init__` 建 `_ext_assess_cache`，`run()` **开头**重置（必须在
  `_route_by_decidability` 之前，否则会把刚填进去的那条抹掉），
  薄壳 `_cached_ext_assess`，两处调用点改走它。
- **边界**：失败**不缓存**（异常照原样上抛，交给调用点既有的 except）；
  跨运行不复用。
- **⚠️ 运行期可见变化（必须说清）**：改前两次评估是**两次采样**（温度 0.2），
  路由那次的结论与拆解那次的结论可能不同；改后**两者恒为同一个值**（路由
  那次的样本）。外判是 (问题, 配置) 的函数、与池无关，所以不是"拿到过期的
  池形状"；但 `_divergent`（池判 vs 外判）的取值会因此**比改前更稳定**。
  方向是好的，但不能只当"省了一次 token"。

### P1 · F7 兑现「完整 evidence」

- **根因**：v1.21.70 [J] 在 changelog 里写明「缓存值用完整 evidence 算、
  重算路径读的是 `evidence[:8]`，两者会不一致」—— **只写了没改**。
- **做法**：池评估返回值新增**加性**键 `_evidence_full`（不动 `evidence` 本身），
  `_merge_decidability` 的兜底重算优先用它；两处注释同步。
- **为什么这条重要**：`_und_untraced` 直接进 `_normalize_decidability` 的
  输入，「无追溯」的条目会被**剔除采信** —— 口径不同就是判定不同。

### P2 · F8 两份调度实现（方案 A：加检测器，不合并）

- **做法**：两份实现都留；`_auto_plan` 的 docstring 显式标注与模块级
  `auto_plan`（= `plan_orientation` + `plan_resources`）的关系与共同规则；
  新增一致性冒烟 `check_v71_auto_plan_agreement`。
- **未采纳方案 B**：统一成唯一实现要把 `llm` 参数贯通
  `plan_orientation` / `plan_resources`，改动面大，属架构批。
- **诚实说明**：这是**报警器**不是"修好了"。本项目最贵的坑就是双实现漂移，
  这一版只保证"一旦漂移就会被冒烟抓住"。

### P2 · F9 `_STOPWORDS` 是一组字符不是词

- **做法**：拆成 `_STOPCHARS`（原单字集合，**保留**、当前无引用）+
  `_STOPWORDS`（**按词**匹配的 21 个多字停用词）。`_tokenize` **一个字都没改**。
- **⚠️ 运行期可见变化**：`_tokenize` → `_kw` → `key_terms` / 相似度全线受影响。
  内容词不受影响（实测「螺旋 / 结构 / 整理」仍在）。

### P2 · F10 `coverage_parts(pool, {})` 的隐式假设

- **做法**：签名改 `cfg: Optional[dict] = None`（docstring 说明本函数当前不读
  cfg）；调用点改传 `self.config`。

### P3 · F11 收尾不再重复写 position 诊断

- **做法**：`_quality_check` 加关键字参数 `write_diag: bool = True`；
  圈内调用**保持默认 True**（行为不变），收尾复核传 `False`；
  压制时打一条 `logger.info`，**不静默**。
- **观测到的副作用（如实记）**：在 mock 那一跑里 dump **全部**来自收尾站点
  （圈内候选 position 交替、本来就不触发 `all_same`），所以改后该跑不再产出
  诊断文件。取舍：诊断的对象本来就不是"合并后的候选"，
  真要两份都留，正确做法是**按内容去重**而不是按站点关一张 —— 归可观测性批。

## 六、经验教训（本版新增）

1. **"外部清单说 X 也有同样的问题"必须实测**。F3 的 `_build_inp_duel`
   就是反例：两张表/两条通道看着像同构，实际池的来源根本不同
   （固定 `[0,1]` vs 跟随 entry）。
2. **"数值指标会变差/翻倍"要看清判据的载体**。F11 的"文件数翻倍"既没被
   复现，本身还不可靠（秒级时间戳撞名）。**判据要取"尝试次数"而不是"落盘个数"**。
3. **条件收窄/放宽类改动，必须先问"出口通不通"**。F1 只改了一个条件，
   但如果只验"字段回填了"，就发现不了"产物 md 的标记写法跟日志侧不一样"。
   **两端（日志 / 产物）都要验，且各自的串要分别 grep**。
4. **修 A 项可能给 B 项制造新的现场**。F1 让单圈层进收尾 → 收尾诊断会
   从 0 变 4 份；F11 正好挡住。**同一批里改了互相耦合的两处，要在报告里
   把耦合关系写出来**，否则下一轮会以为 F11 是多此一举。
5. **缓存类修复有"第二语义"**：F6 不只是省一次调用，它把"两次采样"
   变成"一次采样"。**省钱的改动要顺带说清它改变了哪个分布**。
6. **判断"没有一条逻辑写两遍"不能靠读**。F1 这个坑（serial 与 B 两处
   `> 1` 门）外部清单只点了 serial 侧一句，另一处是我 grep `> 1` 找出来的。
   `grep 形态` 比读清单可靠。
