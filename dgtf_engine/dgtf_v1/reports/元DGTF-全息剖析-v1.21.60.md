## 一、设计方向

**一句话定义（蓝图原文，`元DGTF整体框架.md:5-6`）**：
> 元 DGTF 是一个**自相似的、四相完整的、方法统一的、默认全留但可覆盖的、
> 三通道记忆的、领域开放的、会记得自己的** DGTF。

**核心转变（`三层递归蓝图.md:16-24`）**：
```
从：修行跑一遍 → 研究跑一遍 → 对撞一次
到：修行螺旋 → 研究螺旋 → 对撞螺旋     ← 三棵独立的树，同一根
```
对撞不再是"前两步之后的一次操作"，它是**第三个独立螺旋**，与前两者平级，
只**输入依赖**它们的产物。

**三层各自的"没碰"是不同的东西**（这是整个设计的题眼）：

| 层 | 名 | 本质 | 状态 | 池 | 能不能永久 |
|---|---|---|---|---|---|
| 修行 0 | 主动悬置 | **决定** | active/stable/resolved/revoked | `suspensions` | **能** |
| 研究 1 | 延迟债务 | **债务** | deferred/handled/escalated/dropped | `deferrals` | **不能**（必须清算）|
| 对撞 both | 悬置张力 | 裁决 vs 悬置**两独立字段** | quadrant | `duel_suspensions` | — |
| 元 all | 决定不消解哪类张力 | 终点 | — | `all 池 = 总池` | — |

**总设计取向可归纳为三条**：
1. **"静止"不是"达成"**——所有停止条件都判"不再变化"，不判"任务完成"
   （`元DGTF整体框架.md:245`、`:8` 的 G1–G11）。
2. **诚实优先于漂亮**——反漂亮约束、允许空、未生走通全程、self-check
   **观察不改**、失败必须留痕（`:462-483`）。
3. **判定权不交给 LLM**——探针筛选用纯规则不过 LLM（`:169`）；
   覆盖率等指标要求"代码实算"口径。

**🟢 值得注意**：蓝图的「必须守住的底线」8 条（`三层递归蓝图.md §六`），
逐条核对当前代码**全部守住**（另附证据见本报告附录 A）。

**🔴 但蓝图自身已经开始滞后于代码**：v1.21.59 主动推翻了蓝图两处——
① §二「escalation 立刻挪、**单向不可逆**」→ 改为三态双向可转；
② 此前 `per_entry` / `new_item_similarity` 0.75 也已被改（现 0.55）。
**蓝图没有跟着改**，现在文档与代码在这一点上互相矛盾，
而代码里的注释仍在引用"蓝图 §二"作为依据（`元DGTF-V1.21.60.py:3001` 附近）。

### 三个结论

**结论 1（🔴→🟡）：约 62% 的层收尾是被截断的 —— 这个数已过期，现值 40%。**
产物口径：体力耗尽 50 次 vs 真实自停 30 次。日志口径：29 vs 7。
当时据此说"大部分层的成本由预算上限决定"，但那批样本只有几十份。
v1.21.59 已把默认 `hard_max` 从 3 提到 12 缓解了这一点（四层停成 12/8/10/5，
3/4 层自停），且"截断"本身不是一个有意义的信号——它只说明"预算比自然
停止点短"。

> 🔴 **2026-10-02 重算（`_convergence_matrix.py`，全量 461 个层实例）**：
> 截断（走满 + 预算）**180/461 = 39%**（当前配置口径 176/445 = **40%**）；
> 自然停止里"安住"38.0%、"空转"19.1%。**多数层的收尾现在由判据说了算**。
> 「62%」这条已被悬空，别再往下引。降级处理：`hard_max` 3→12 的缓解确有其事，
> 只是没夸张到能把主次逆过来。

**结论 2（🟡→🔴）：一批机制是"零触发"，但要分两类看。**

| 类型 | 例子 | 判断 |
|---|---|---|
| **守卫型，本就不该常触发** | min_rounds 拦截(0)、债务 dropped(0)、元层语义下限(2) | 🟢 可接受，但**等于没被验证过** |
| **本该触发却没触发** | 双通道均收敛(0)、双通道均停滞(0)、漂移标记(0)、both 配额(0) | 🔴 **可疑**——要么条件太苛，要么实现有问题 |
| **设计如此** | 四象限对齐成功 = 0 | 🟢 **不是缺陷**：文档已定案"未对齐是合法结果"，且实测最高配对相似度只有 0.18（降到 0.3 也是 0 命中）→ **表征问题，不是阈值问题**（`元DGTF整体框架.md:198`）|
| **新机制，无真跑** | 可判定性转移(0)、复债(0) | ⚪ **只有单测 + 回放**，v59 里一次 escalation 都没发生 |

> ⚠️ 特别提示：「漂移标记 0」我上一轮曾据此认为"P2-3 从未触发、值得复查"，
> 后来发现**更可能是它本来就极少有机会**。这类"0 次"在下结论前必须先确认
> **条件是否可达**——v1.21.58 那次 `max_uncovered_pushes` 的 A/B 就栽在这里。

**结论 3（🔴）：机制之间的口径分叉是本项目的系统性问题，不是偶发。**
本轮我亲手修的有两处，都是"同一份逻辑只在一处生效"：
- 三态归一化**只有外部评估有**，池评估与合并都没有（`_assess_decidability`
  vs `_assess_decidability_from_pool_view` / `_merge_decidability`）；
- 「欠一个答案」的集合**只有喂模型的 shape 认 `partial`**，覆盖率分母不认。

## 四、功能（含可达性）

### ✅ 覆盖面确实很宽
- **15 个 CLI 参数**（12990–13018），**无死参数**（全部有消费点）。
  `--rounds` 默认 `"0"` 的语义已核实：**不是 0 圈，是"每层用配置的
  hard_max"**（`_rounds_plan` 9074）。
- **配置**：YAML 叶键 81 个 / `DEFAULT_CONFIG` 85 个。
- **交互模式存在**（12904）：问 route / rounds / channels / parallel / 显示选项，
  **但不问 cost_profile 与 keep**。
- **产物**：一份真跑产物 **100–141 KB / 约 1400 行 / 54 个标题**，四个层各一段。

### 🔴 但"出口"很窄
- **无批量**（`question` 是 `nargs=*` 拼成一个字符串，13081）；批量只能靠

  这个注释会误导人（"## 这一次我是谁"只是**单次运行内**各层 view 的累积）。
- **4 个死配置**（**已复核**）：`output.plain_speak` / `output.layer_summary` /
  `actions.plain_speak` / `actions.summarize_views`。证据：这三个名字在
  `元DGTF-V1.21.60.py` 里只出现在**别名表**（2643–2644）与 **DEFAULT_CONFIG**
  （12495–12496、12531–12532），以及 yaml；而全部 `_action_on(...)` 消费点
  只有 13 个名字（`assess_decidability / decompose_question / dual_judge / he /
  ing / input_sanity / manifest / parallel_expand / phase_probe / re_anchor /
  re_evaluate_pool / self_check / settle_research`）——**没有它们**。
- **配置被硬编码覆盖**：A 模式写死 `_upstream_provider=lambda e: []`(10236)

## 五、可靠性

### 🔴 最严重的三个点（均已复核）

**1. 并行模式下"某层整层消失"且测试永远发现不了。**
B/C/D–H 里某层第 1 圈若抛异常（如 LLM 重试耗尽 `raise RuntimeError` 4177-4206），
`state["stopped"]=True` 但 **`self._results[entry]` 永不写入**（10426/10639/10811
才写）；`_b_finalize_layer` 见 `state["view"] is None` 直接 return
（11632-11633）→ **该层从 `views`/`pools`/self 段彻底消失**，下游静默跳过。
而冒烟的"层数校验"用的是**实际 views**（2043-2044）→ **层真缺了它也自动缩减，
永远判不出**。`dg.run` 这几处（9586 / 10629 / 10800）**都没有 try**。
（A 模式则留一个空壳 View，10276-10280——两种模式行为还不一致。）

**2. 跨层共享池存在无锁读。**（已复核）
`_align_suspensions_and_deferrals(self.pools["0"], self.pools["1"], sp)`
在 9506 与 11084 两处被调用，**都不在 `with self._pool_lock` 里**；
而 both 层线程读这两个池时，0/1 层线程正在 append（`Pool.merge`）。
→ 四象限匹配率/象限可能**每次运行都不同**，并经 `_probe_duel` 影响产物。
这与项目"可独立复现是**可检验性的基础**"（蓝图 §四）直接冲突。

**3. serial 无逐圈隔离，单圈异常吞掉整轮。**
9586 / 11896 无 try；只要 `_expand`(4451) 或 `_render`(4642) 有一次
未被内部兜住的异常，`_run_layer` 直接抛出，main 丢弃 result
（12961-12966）→ **零产物**（不是"缺层"，是"什么都没有"）。

### 其他
- **`except: pass`（仅 pass，无 log）9 处**（另有 1 处是合法的可选依赖
  `except ImportError`）：4217 / 4462 / 4514 / 5398 / 8365 / 8379 / 9595 /
  10945 / 11485 —— **已复核**。
- **测试盲区（零覆盖）**：LLM 重试耗尽 / `parse_json` 畸形 /
  `pipeline_gate_timeout` 超时 / `save_result` 落盘失败 / `load_config` 非法 /
  某层抛异常 / **同输入跑两次是否一致**。
- **测试构成**：18 个 `check_*` + 9 模式端到端循环，**53 项 ✓**。
  但其中 **6 处**是"扫源码文本"的断言（`SRC.read_text` 计数；如要求
  `stop_reasons: List[str] = []` 恰好出现 2 次、块长 20–160 行）
  —— 这类断言**只验文本不验行为**，改名/空行/注释都会假红或假绿。
  本轮我一次就踩到它（docstring 反斜杠导致源码摘除失败 → 两个历史检查误报）。
- **确定性**：serial/A 结构确定，B 按 barrier 确定；**C/D–H 结构性不确定**
  （provider 读活表 `_results`，下游读到上游第几圈取决于谁先跑完；
  `views`/`dispatch.order` 的键序 = 完成序）。

## 六、价值

### 交付物是真材实料（有正面证据）
真跑产物：**100–141 KB / ~1400 行**，四层各一段，每层有"没看清 / 撞不动 /
决定不碰"三类严格区分，末尾「池」与「悬置总览」。

**一份成功的产物长这样**（`20260930_010533_2024年欧盟AI法案对高风险AI系统的.md`）：
> 子问题1（协调标准尚未出台时，高风险AI系统的合规性如何成立）：答案落成两串
> 已列项的清单。欧盟那侧是**风险管理系统、数据治理、技术文档、记录保存、
> 透明度与信息提供、人类监督、准确性鲁棒性与网络安全**。协调标准未出这个前提，
> 没有改变这串清单本身的成立方式——清单照列，位照占。

这段是**可核对的事实**（确为欧盟 AI 法案高风险系统的法定要求清单），
`answered=[1,2,3]`。所以系统**不是空转的**。

### 但价值的稳定性不足
- **24 份可解析产物里，19 份至少答了 1 个子问题，5 份答 0 条**。
- **13/30 产物没有「质量线索」段**（该段是条件渲染）。
- 有标记的产物里，**`position_all_same_structural` 出现 12 次**——
  这是"对偶判断的 position 维全落在同一结构上"，即**蓝图「五条真」的第 2 条
  "每个候选都真的判了双维"被系统性违反**。它反复出现，说明不是偶发抖动，
  而是**输出形态的稳定倾向**。
- v59 那次抽象题（"整体到底是什么"）**末态没有可判定答案**；
  换成可判定性更强的题（欧盟法案）同配置给 3/3 → **题目敏感**。

### 成本
单题 **125–333 次 LLM 调用 / 18–47 分钟**（取决于预算档）。
而按结论 1 的**现值**（40% 截断，2026-10-02 全量重算；原文写 62% 已过期），
**约四成的调用花在"注定走满"的圈上** —— 少了将近一半，但仍是最大的一块可省的
成本，且这笔钱花在哪一层是可查的（"空转"19.1% 那部分是另一回事：那是判据
让停的，不是预算逼停的）。

## 七、综合判断

### 一句话
**设计方向清晰且诚实（8 条底线全守住），架构可运行、交付物有真价值；
风险不在"想错了"，而在"实现了太多、验证得太少"——
机制数远超真跑验证量，且关键路径存在静默失败面。**

### 按优先级排序的账（我的建议顺序，供你定）

| # | 事项 | 轴 | 为什么排这个位置 |
|---|---|---|---|
| 1 | **建"层缺失"守卫**：并行模式某层异常必须**留痕 + 报错**，冒烟改成**按请求的 route 校验层数**（不用实际 views） | 可靠性 | 现在会**静默丢整层**且测不出；这是唯一"错了却看不出来"的问题 |
| 2 | **真跑看分类分布**（v1.21.60 占位段已写） | 机制 | v1.21.59 三条修正**全无真跑证据**；归一化后分类是否一边倒偏 partial 直接影响后续所有指标 |
| 3 | **给 C/E/G/H 至少各跑一次**，或明确宣布它们不受支持 | 功能 | "9 模式"是卖点，但 4 种从未真跑；不确定性也只在这 4 种里 |
| 4 | **跨层池读加锁**（9506 / 11084） | 可靠性 | 破坏"可独立复现"，而对撞/元的输入就建立在它上面 |
| 5 | **停止判据两块实现收口**（`_run_layer` vs `_b_check_stop`） | 机制 | 本项目第一大结构性风险；现在只靠"理由字面量"守卫 |
| 6 | **清理误导性声明**：`dgtf_config.yaml:456`「跨问题累积」、4 个死配置、`_pack_lock` | 功能 | 低成本、但注释会误导人（我已经被它误导过一次） |
| 7 | 蓝图同步：把已推翻的 §二「单向不可逆」等改掉 | 设计 | 否则后续每轮都在"引用一份已经作废的蓝图" |

### 我不建议现在做的
- **不要再加机制**。零触发的机制已经有一批（双通道收敛/停滞、漂移标记、
  both 配额…），再加只会让"实现 ≫ 验证"的缺口更大。
- **不要靠调阈值解决"零触发"**。四象限那次已经证明：0 命中不是阈值问题
  （实测最高配对 0.18），是表征问题。同样，先查**条件可达性**再谈调参。

### ⚪ 我没能验证的
- `DGTF.outputs`（69 份）与前两批字段体系完全不同（JSON 式），
  **不可跨版本对比**，那批数据的价值我无法评估。
- "C/D–H 结构性不确定"我复核了代码路径（provider 读活表），
  但**没有跑两次同输入对照**来实测差异。
- 12 个真跑的 `views` 里是否有层缺失：我只确认了**机制上会静默缺层**，
  没有逐份核对历史产物是否真的缺过层。
