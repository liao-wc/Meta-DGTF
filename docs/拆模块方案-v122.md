## 一、依赖分析（实测）

| 指标 | 实测值 |
|---|---|
| 顶层符号（函数 / 类 / 模块级常量名） | **201** |
| 依赖边（符号体里出现别的顶层符号名） | **384** |
| 双向边（互相依赖 —— 成环的强证据） | **10 对** |
| 跨候选模块边 / 总边 | **185 / 384 = 48%** |

口径说明：这是**词法近似**（扫符号源码片段里有没有别的顶层名字），
不解析作用域，也不区分「调用」与「只在注释里提到」。它的用途是
**找环**和量级，不是做编译器。真到动手那一步要换成基于 `ast.Name`
+ 作用域解析的图。

### 候选模块的符号分布

```
other 136 · render 18 · decidability 12 · main 12 · pools 9
anchors 4 · meta 4 · config 3 · spiral 2 · llm 1
```

`other` 占 136/201 —— 这本身就是结论：**当前命名没有形成模块边界**，
大多数符号既不属于渲染、也不属于可判定性或锚点。所以第一步不是拆，
而是**先给 `other` 立命名法**（谁属于 spiral、谁属于 lifecycle）。

### 环（双向依赖，10 对）

```
DGTF <-> LLM                DGTF <-> Pool
DGTF <-> dump_view_fields   MetaDGTF <-> Pool
MetaDGTF <-> main           _pool_meta_summary <-> _render_landing_boundary
_render_landing_boundary <-> render_landing   _render_landing_decision <-> render_landing
_reopen_closed_debt <-> apply_decidability_change
coverage_of <-> coverage_parts
```

前 5 对是**结构性的**（引擎 ↔ 依赖对象 / 入口），拆模块时必然出现，
需要靠依赖注入或协议接口解。后 5 对是**薄封装 ↔ 被封装**：
`coverage_of` 只是 `coverage_parts` 的一行壳；`render_landing` 只是分流壳
（v122 阶段 3 刚做的）；`_pool_meta_summary` 是阶段 3b 抽出来的共用实现。
这三对**不是坏味道**，是同一条规则两处命名 —— 拆模块时按「谁被谁调」
定向即可，不需要为它们引入接口层。

## 三、迁移步骤（若下一版要做）

1. **先立命名法**：把 `other` 里 136 个符号按上表归类，只改注释分组，
   不搬代码 —— 这一步不产生 diff 之外的任何风险。
2. **抽 `config` / `llm` / `pools`**：这三块出边多、入边少（被依赖，
   不依赖别人），是天然的第一刀。
3. **抽 `decidability` / `anchors`**：它们是 v1.21.73 起才长出来的，
   与老代码耦合面最小。
4. **`render` 最后抽**：它依赖几乎所有人（21 条跨模块边里最多）。
5. **`MetaDGTF` / `DGTF` 留在 `dgtf.py`**：它们是编排层，抽出去会把
   环形依赖放大。

## 四、风险与回退

| 风险 | 说明 | 回退 |
|---|---|---|
| 环形依赖放大 | 实测已有 10 对双向边；拆开后会变成跨模块 import 环 | 保留薄 shim（见第五节），先不删原文件 |
| 单文件红线被破坏 | 本项目所有探针/冒烟按**单文件路径**加载（`spec_from_file_location`） | shim 保持同一路径可加载 |
| 隐式全局状态 | 模块级 `logger` / `_PARALLEL_CONF_MIN` 一类共享量 | 集中在 `config` 模块导出 |
| 产物逐字漂移 | 渲染层搬动会改 `save_result` 的调用栈 | 用第六节的 AST 等价方案核 |

## 五、兼容策略：薄 shim

`元DGTF-V1.22.0.py` 保留为**薄 shim**：import 全部子模块 + `main()`，
`__version__` 保持不变。这样：

- 现有 27 个探针 / 6 条 `check_v122_phaseN` / `_v122_verify.py` 全部
  不用改（它们只认这个路径）；
- 出问题时 `git checkout 元DGTF-V1.22.0.py` 立刻回退到单文件形态。

## 六、AST 等价验证方案

拆模块**不能**用「基线 vs 新版」的 AST 全等来验（文件结构本来就变了）。
可执行的方案是三层：

1. **符号守恒**：新版各模块导出的符号并集，必须覆盖旧版全部 201 个
   顶层符号（`mechanism_removed()` 已经能做这件事，改成「集合包含」）。
2. **函数体哈希守恒**：对每个函数，用 `ast.dump` 归一化（去掉行号）
   算哈希，逐个比对「搬动前后是否逐字同一份 AST」。不同则必须在
   差异清单里逐条解释。
3. **行为守恒**：`_probe_v122_phase6.py` 那套「打桩 + 固定输入 +
   逐字段对照」扩到全部探针（本版已有 27 个探针可复用）。

## 七、探针 / 冒烟的兼容性核对

| 依赖形态 | 数量 | 拆模块后是否可用 |
|---|---|---|
| `spec_from_file_location(<单文件路径>)` 加载 | `_v122_verify.py` + 27 个探针 + 6 条冒烟 | ✅ shim 保持路径不变 |
| `grep 源码字面串`（`_v122_verify.py` 的多处判据） | 12 处 | ⚠️ 拆开后字面串会分散 —— 判据要改成「按模块 glob」 |
| `inspect.getsource(mod.X)` | 8 处 | ✅ 只要 `mod.X` 还在 shim 的命名空间里 |
| `count_del_lines` / `mechanism_removed`（按单文件比） | 2 处 | ⚠️ 要改成「多文件合并后比」 |

**结论**：拆模块真正的成本不在搬代码，而在**改判据**——
12 处字面串判据 + 2 处单文件比对要先改成多文件口径，否则拆完冒烟必红，
而且红的原因全是判据不认路径，跟行为无关。

## 八、本版决定

**不拆。** 理由：

- 本版已经改了 6 个阶段、新增 27 个符号，再叠一次结构搬迁，出问题时
  「是搬迁错的还是阶段改错的」分不开；
- 48% 的跨模块边说明现在的耦合度不适合直接切；
- 上面第七节那批判据改造是**前置条件**，属独立一批工作。

下一版候选：先做第三节的第 1 步（立命名法，零风险），再评估第 2 步。
