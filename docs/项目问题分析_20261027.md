# 项目问题分析（基于产物证据，2026-10-27，Round 131）

> 数据源：`outputs/` 359 个 packed（2026-10-09 ~ 10-26）、`docs/ab_results.jsonl` 145 行、
> 场景矩阵 live、重放/过程门/app/ui/完整性快照。方法：脚本 `scripts/project_analysis.py` 全量扫描（零 API）。
> 结论先行：**门禁与机制单元测试是绿的（15/15），但产物层证据暴露 4 类系统性问题：验证语义不可靠、
> 过程告警过载、经济效率低、溯源与合并缺口。**

## 一、规模与效率（成本视角）

| 指标 | 数值 | 判断 |
|---|---|---|
| 历史 packed | 359 个 | 大多为重复/实验产物 |
| 累计 tokens | **240,407,508** | 按窗口差计费，历史单跑平均 67 万 tokens |
| 重复问题额外 tokens | **154,391,481（64.2%）** | 65 个问题被重复跑（最多 46 份）→ **最大浪费源** |
| unverified 跑次 tokens | 32,920,241（13.7%） | 花完预算仍无可用答案 |
| 被截断（体力耗尽）跑次 | **29 条 / 25,442,826 tokens（10.6%）** | 预算耗尽≠自然收敛，质量不可信 |
| A/B 记录 | 145 行，其中 **97 行缺 cost 字段** | 成本核算不全；packs 359 vs AB 145 → 214 个产物无质量/成本对照 |
| A/B 质量分布 | 历史实验档 0.18~0.26（b1/r1/cache/mem） vs 近期 0.93~0.99 | 记录混入大量失败基线，无统一"项目质量"口径 |

**问题 P1：经济效率。** 64% tokens 花在重复问题；29 条截断跑次没有产出可用答案；
A/B 成本字段缺失使单位成本无法核算。若按"只保留每问题最新/最优一份 + 缓存命中"，历史花费可大幅压缩。

## 二、质量与验证语义（最重要）

| 指标 | 数值 | 判断 |
|---|---|---|
| verified 趋势 | 10/22 28.6% → 10/24 66.7% → 10/25 57.4% → **10/26 73.3%** | 近期有提升，但未收敛 |
| coverage 均值 / <0.8 / <0.5 | **0.5609** / 257 / 124（共 283 条有读数） | 大部分产物"覆盖面不足"，质量问题不是个别 |
| fact_card ok | **139 / 359（38.7%）** | 六成产物的事实卡未闭环 |
| 三态 α（tri_alpha） | n=283，均值 **0.0565**，不可靠 **248（87.6%）** | **三态一致性基本不可读**；该机制尚不能作为质量证据 |
| display 覆盖 | 116 / 359（32.3%）；**verified 但无 display 57/150（38%）** | 答案展示层不完整，用户可见答案与质量结论脱节 |
| 题型 | fact 161 / reasoning 61 / decision 8 / unknown **127（35.4%）** | 老包缺 answer_summary，分析口径被污染 |
| 各题型 verified | fact 105/161（65.2%）；reasoning 38/61（62.3%）；decision 6/8 | **reasoning 的 verified 是"过程合同验证"，不是答案正确性**——命名被过度解读 |

**问题 P0：验证语义。** `verified` 在事实题=官方源/答案质控，在 reasoning=过程合同（非答案正确性），
二者同名却语义不同；`tri_alpha` 87.6% 不可靠说明"三态一致性"尚未成为有效证据；
38% verified 产物没有 display 让用户无法核验。

## 四、溯源与一致性（可复现性）

- **0/359 个 packed 有 engine version / git SHA**（只有 `_config`、`_runtime`）→ 质量变化无法归因到代码版本；
- 127 个包缺 `answer_summary`（老 schema）→ 同一分析口径下 35% 不可用；
- 场景矩阵：60 行中 **58 行有 live 锚点、2 行无**；max|Δ|=0.052，已逼近 0.06 护栏阈值（漂移风险）；
- 审计快照新鲜（replay/process_gate 5:46、integrity 5:47、app/ui ok），但文件名仍带 `20261025` 日期；
- A/B 记录 1 个重复 tag；历史行缺 cost 字段（schema 演进未迁移）。

**问题 P2：产物溯源缺失。** 没有版本指纹 → 无法回答"这次质量变化来自哪次改动"，
也无法安全淘汰旧包/做 A/B 归因；矩阵锚点仅 58/60 且逼近阈值。

## 五、产品/交付层

- 32.3% 产物有 display；verified 无 display 57 条 → **最终答案展示仍是短板**；
- 1 个 packed 缺 .md（replay 基线，可接受）；md 平均 115KB，部分超长；
- 输出目录无保留策略：359 packs/321MB，重复 65 题（max 46 份）；
- 本地模型：self_check_min 默认 v9b、self_check 槽 v8b；30 条 held-out 质量与 v8b 持平（字段 0.589），
  **本地模型尚未带来答案质量增量**，只带来延迟/离线收益；dual_judge local 吞吐不足（8 次回退）；
- 文档：并发会话持续新增 17+ untracked docs；历史文档与当前面文档曾混用数字（Round 128 已修当前面）。

**问题 P2：交付一致性。** 展示层（display）、保留策略、文档索引三处未收口；
本地模型价值主要体现在成本/延迟，不在质量。

## 六、结论与优先级

| 优先级 | 项目问题 | 建议 |
|---|---|---|
| **P0** | `verified` 语义分叉（事实 vs 过程合同）+ tri_alpha 不可靠（87.6%） | 质量字段拆分为 `answer_correctness_verified` 与 `process_contract_verified`；tri_alpha 不达标时不展示为质量证据 |
| **P0** | 64.2% tokens 花在重复问题；29 条截断跑 | 问题级去重/缓存优先、单问题保留最新最优；预算截断前强制"可交付答案"检查 |
| **P1** | duty_short 76.6%、probe 悬空 46.8% | 按题型/层校准判据阈值（需真跑样本）；告警分级（block/warn/info） |
| **P1** | display 覆盖 32.3%、verified 无 display 38% | display 作为 ready 的必要条件，或明确"无 display 不算 ready" |
| **P2** | 0 版本指纹、127 老 schema、58/60 矩阵锚点 | 产物写 engine version+git SHA+config hash；老包归档；矩阵补 2 行锚点 |
| **P2** | A/B 145 vs 359、97 缺 cost、1 重复 tag | 统一 A/B schema；历史行标注 legacy；成本以 usage 为准落 pack |
| **P3** | 输出无保留策略、文档碎片化 | 保留策略 + 文档索引（本轮已提交分析脚本与 JSON） |

**一句话：项目的问题不在"有没有机制"，而在"证据链不可信、经济效率低、交付不完整"——
先修 P0 语义与成本效率，再校准过程判据，最后补溯源与展示。**

## 十三、Round 136–137：dual_judge local 适配层（吞吐止损）

针对"v3 质量已升但端到端 8/8 回退、单次 22–45s"的问题，改**调用适配层**而非继续压 token：

| 改动 | 内容 |
|---|---|
| 候选截断 | 每次本地调用只判前 **12** 条（prompt ≤4000 字符，避免长尾） |
| 输出压缩 | schema 只要求 `{"judgments":[{idx,position}]}`（不要求 why，落值 why 允许空） |
| token | max_new **320→192**（压缩 schema 下 ~24s/次） |
| salvage | 优先用服务端 `json`（截断抢救结果），减少"text 解析不出 JSON" |
| 覆盖率门槛 | 命中 ≥70% 才接受，防部分落值造成质量漂移 |
| 熔断+预算 | 模块级：连续 2 次失败 ⇒ **300s 冷却**；每个 run 最多 **2 次成功调用**，其余动作直接回退 llm |

**真实验证**：

| 跑次 | 质量 | 本地双判 | wall | 窗口差 |
|---|---|---|---|---|
| HTTP304（旧，v3/8 次尝试） | 0.9732 verified | 8/8 回退 | 371.0s | ¥0.49 |
| HTTP301（v1 适配） | 0.9497 verified | 9 次失败 | 341.7s | ¥0.53 |
| **HTTP302（v2 适配：熔断+预算+salvage）** | **0.9693 verified** | **2 次 503 即熔断 + 1 次跳过** | **242.9s** | **¥0.26** |

⇒ wall 相对旧版本 **−35%**（371→243s），本地调用尝试 9→3、成本减半；质量保持 verified。
本地"接管"仍为 0（服务被 503 判忙），但熔断保证不再把时间耗在反复重试上——
dual_judge local 作为 opt-in 的**有界开销**模式可用；接管需服务侧并发/吞吐进一步优化。

仍是遗留：judge 本地真实接管率（需服务并发/批量设计）、self_check 质量增量、tri_alpha 测量学、legacy unknown 包。
