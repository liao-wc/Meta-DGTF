口径（四个问题分开答）：

1. **跑了没跑**：`views` 里有该层 key **不等于**该层跑了。判据 = `view.rounds_run > 0`。
   短 route 会把上游层 view 携带进产物（如 `--route 1` 带 layer 0 的 view）——
   例子：`20261028_122642` 的 views 有 `0` 和 `1`，但 layer 0 的 `rounds_run` 缺省
   ⇒ 记为「仅携带，没跑」。
2. **读数有没有**：主读数是引擎 `_LG_KEYS` 那一条
   （0:`excavate` / 1:`settle` / both:`fuse` / all:`crystallize`）。来源优先级：
   落盘 `goal_now` → 旧版 `goal_verdict` 文本 → **审计脚本内的独立复算**
   （与引擎同公式、但独立代码，**不调用引擎 `layer_goal_readings`/`_lg_*`** ——
   否则引擎改公式、落盘还是旧值，自己校验自己永远绿）。
   V2.2.12 之前没有 `goal_now` 出口，只能这样读旧包；两种口径分开列，不混。
3. **读数是多少**：见 §2、§3 的分布与依据字段。
4. **够不够达到目标**：用引擎**自己的** `layer_goal_stop_signal` 判定
   （0: `excavate` < 0.10 且 `n_aspects`>0；1: `settle` 连续 2 圈不涨；
   both: `fuse` 连续 2 圈不涨 / `sem_stagnation` ≥ 0.80；all: `crystallize` = 1.0）。
   同时单列**运行中停因是否命中**（`stop_reason` 文本里真的写过「目标已达成/受阻」）——
   「最终视图按当前口径判达成」与「运行中判据触发过」是两件事，分开报才不会互相冒充。

## 4. 关键发现（区分「模型能力不足」与「读数/口径/接线缺陷」）

### 4.1 零 LLM 跑次：四层「跑了」，但读数不是模型给的（V2.2.14, 12:55）

`outputs/_e2e_local/20261028_125517_水的三态变化有哪些驱动因素.packed.json`：

- route=0+1+both+all，四层 `rounds_run` 都是 2，**`llm_calls=0`**、
  `llm_cb_opened=1`、`llm_cb_skipped=47` ⇒ 8773 适配层已死，熔断器打开，全部调用被跳过；
- 四层 verdict 都在：层0/1/both「未测出（原因可指认）」，all `crystallize=0.500`；
- 层0 `aspect_hist=[0,0]`、`aspect_units=0`；层1 `settlement=0/0`；both `n_new=0/upstream=0`。
- 结论：**这次不是模型能力不足，是链路故障（零调用）**。它同时证明「跑了必有说法」的
  诚实化通道（V2.2.12）有效：零数据时不伪造读数，且给出可指认原因。
- 全程共 **5 个零 LLM 跑次**：`104816/104940`（V2.2.13 route=0）、
  `105007/105033`（V2.2.13 route=1）、`125517`（V2.2.14 四层全跑）。

### 4.2 元层（all）的「达标判据」在圈内**结构不可达**（接线/时序缺陷）

- 200 个真跑 all 层里，最终读数 `crystallize=1.000` 的有 **194** 个；
- 但 `goal_trace` 逐圈主读数最大值分布：**0.500×194 / 0.000×5 / 0.250×1**
  —— **没有任何一次在圈内读到 1.000**；
- 历史 31 次「目标已达成/受阻」停因命中里，**元层 0 次**；
- 直接证据：125517 的 `goal_trace=[{crystallize:0},{crystallize:0}]`，
  而最终 `goal_now.crystallize=0.500`；`20261026_170458` 逐圈 0.5/0.5/0.5，最终 1.000。
- 根因（读源码）：`view.meta_closure` 在**层收尾**（`_finalize_layer_common`）才赋值，
  而逐圈判据 `_layer_goal_now`/`_goal_stop_signal` 在**每圈结束**就跑；
  收尾的「目标读数刷新」只刷新 `goal_now/goal_verdict`，**不回写 `goal_trace`、不重判停止**。
  ⇒ `crystallize >= 1.0` 这条停止判据在运行时永远看不到 closure+lookback 两件事。
- 影响：元层「四件事齐 = 结晶完成」这个**停止依据形同虚设**（不是没数据，是数据晚到）；
  最终产物仍能读到 1.000（收尾刷新），所以这是**判据接线缺陷**而非读数缺陷。
  引擎源码归 Lead，本轮只报告、不改。

### 4.3 层1/层both：**圈内判据的尺子 ≠ 收尾读数的尺子**（同一读数两处口径）

| 层 | 逐圈读数最大值 vs 收尾读数 | 数 |
|---|---|---|
| 0 修行 | 一致 / 不同 / 只有收尾有 | 6 / 1 / 33 |
| 1 研究 | 一致 / 不同 / 只有逐圈有 / 只有收尾有 | **2 / 189 / 9 / 5** |
| both 对撞 | 一致 / 不同 | **39 / 158** |
| all 元 | 一致 / 不同 | 0 / **200** |

- 层1：`view.settlement` 只在收尾（L22731）赋值；圈内 `_layer_goal_readings` 走
  `covered_aspects/uncovered_aspects` 兜底 ⇒ 圈内 `settle` 与收尾 `settle` 几乎从不同值。
  实例 `20261028_122642`：`goal_trace` 第 2 圈 `settle=0.500`，收尾 `settlement=0/0`
  却判「未测出」——同一次跑里 0.500 与未测出并存，是**两个口径**不是两个事实。
- both：收尾时 `duel_suspensions` 才从池里汇总进 view（L22749），圈内 `fuse` 用的是中间池。
- 结论：层1/both/all 的停止判据读的是**圈内中间态**，收尾 verdict 读的是**最终态**；
  「连续 2 圈不涨」判的未必是 verdict 显示的那条序列。是否改、怎么改（冻结口径或收尾重判）
  需要 Lead 决策（引擎源码归 Lead）。

### 4.4 对撞层（both）分母口径：是「上游层数」，不是「上游层面数」

- `layer_goal_readings` docstring 写「融合率 = 新层面数 / **上游可用层面数**」，
  但实现取 `view.upstream_layers`，其定义是 `len(inp.upstream_views)`
  ——**上游层的个数**（四层跑时恒为 2），不是层面数；
- 数据佐证：195/198 个真跑 both 的 `upstream_layers=2`（另 3 个=0 ⇒ 未测出）；
- 后果：新层面数 ≥2 时 `fuse_raw=min(1, n_new/2)=1.0` 被 **clamp 到满分**
  （196/199 含合成回放；真跑 195/198），主读数退化成 `1 − sem_stagnation`
  —— 它是「复读罚」的镜像，不是「融合生成率」；
- 构造性对照（`20261026_170458`）：`n_new=5, sem_stagnation=0.4615` ⇒
  现口径 `fuse=min(1,5/2)×(1−0.4615)=0.538`；若分母改用上游层面数
  （层0 units 11 + 层1 units 11 = 22）⇒ `fuse=(5/22)×0.5385≈0.122`，差 4.4 倍。
- 附：代码里还有一条死兜底 `both_quota.upstream` —— 当前引擎从未写入该键
  （`both_quota` 只有 ratio/n_both/n_total/max_ratio/items），上游为 0 时这条兜底恒 0。
- 结论：这是**读数口径与 docstring 不符**（docstring 写层面数、实现是层数 + clamp 饱和），
  不是模型融合能力。
- **Lead 裁决（2026-10-28，本会话）**：先按「**代码行为是有意的、docstring 写错**」处理
  —— README 第一节只写「产出率 ×(1−语义停滞罚)」，产出率按饱和型理解（n_new≥2 即满产），
  主读数 `fuse` 语义保持不动，V2.2.15 只修 docstring 并在报告里标 basis，**不改判据**。
  反证检索（供日后复议）：README 第一节、docs/ 全库 grep「上游可用层面数 / 新层面数 /
  融合生成率」均**无**「分母=层面数」的设计表述；唯一写「层面数」的是引擎函数 docstring
  本身（即已被裁决为写错的那处）⇒ **未找到反证**。

### 4.5 默认 2 圈下，层1/both 的「连续不涨」判据结构不可达

- 实测：层1 **145/222**、both **188/200** 判为「判据样本不足」；
- 这不是「读数没有」：层1 落盘读数 196、both 197。
- 层0 的 2pt 口径已在 V2.2.12 修通，2 圈即可判（121624 `excavate=0.000` ⇒ 停因命中「达成」）。
- 结论：**判据/圈数配置缺陷**（默认圈数 < 判据所需点数），不是模型能力。

### 4.7 元层 crystallize 的「0.500」是什么（量 vs 计数的口径观察）

125517 的 `goal_now.crystallize=0.500`、`n_hits=2`，但
`crystallize_detail={closure:true, lookback_items:0, engagements:0, suspensions:0}`：
两件「留痕」都只是**字段存在**（closure 空壳 + 回看 total=0），量全是 0。
⇒ `crystallize` 计数口径对「是否真做了结晶/回看」零区分度；
`crystallize_detail` 提供了量，但**判据/停止信号只读主读数**，量没有进入判定。
本报告只陈述这一读数事实（`crystallize_zero_amount_hits` 1 例），是否调整口径由 Lead 定。

### 4.8 零 LLM 产物判据（12:55 那类跑次不能被读成「模型能力不足 / 挖尽」）

判据三处同口径（均已落地）：

- **审计脚本硬异常**：`zero_llm_achieved`（零 LLM 却判「达成」）、
  `zero_llm_verdict_empty`（零 LLM 跑过的层 verdict 空）、
  `zero_llm_unmeasured_reason_missing`（零 LLM 未测出但原因空）；
- **探针** `probe_layer_goals.py`：`llm_calls==0` 时先过同一判据 —— 合规 ⇒ 记「没跑(exit 2)」，
  违规 ⇒ **判红(exit 1)**（说明诚实化通道坏了，不是没跑）；
- **契约测试** `tests_layer_goal_all.py` G3/G4：真实零 LLM 产物全量回验 + 变异体
  （伪造成「修行层挖尽」必须报违规）。

实测（5 个零 LLM 跑次：104816 / 104940 / 105007 / 105033 / 125517）：

- 跑过的层 verdict 全部非空；未测出全部带可指认原因；
- 按引擎停因判据复算，**没有任何一层被判「达成」**（125517 的 all=crystallize 0.500
  属「未达成」，不是「挖尽」）；
- 结论：这类跑次会被明确记为「没跑通（链路故障）」，不会污染「模型能力」读数。
