# 判据稳定性：根因与修复（2026-10-30）

> 关联版本：V2.2.59（串行锁 + ffc 缓存稳健性）、V2.2.60（锁可重入 + 验收链路）、
> V2.2.61（本文档 + 状态摘要）。零 API 花费。

## 1. 现象

多轮出现「同一份代码、同一命令」时好时坏：

- `test_fused_full_chain.py` 偶发 PASS 23 / FAIL 1（C3–C8 连锁失败）；
- `test_fused_optimal.py` 偶发 29/1；
- 并发跑 e2e / probe / 验收时更明显。

回顾时若只看单次结果，容易误判为「引擎回归」或「环境抖动」。

## 2. 根因（已定位，两类）

### 2.1 并发争用

多个判据同时起临时 App server、抢 8772/8773、写 `outputs/` 目录 ⇒ 端口/文件/时序干扰。

**修复**：`scripts/local_model/_serial_lock.py`（Windows `msvcrt` / POSIX `flock`），
7 个重资源判据共享同一把 `local_chain` 锁；V2.2.60 起锁**可重入**（父进程持锁时
子进程看 `DGTF_SERIAL_LOCK_HELD` 直接跳过），并扩展到 final_acceptance / run_v2_tests /
app_selftest_gate，避免验收串跑器与子判据互锁。

**证据**：并发 ffc+fo ⇒ 25/25 + 30/30；并发验收+ffc ⇒ 30/30 + 25/25（ffc wall 543.6s，
证明实际等待串行）。

### 2.2 ffc 缓存状态耦合（C3 连锁失败的真正原因）

`fused_full_chain` 的主任务问**事实题**（HTTP 404）。预算收紧后 App 会走
`quality_retry`（事实题强制 web-retry）⇒ 缓存被跳过；同时主任务若带 `no_cache`，
该选项经 `_opts_root()` 被 D 组继承 ⇒ D 组（未验证缓存复用）必然失败。

**修复**：主任务显式 `no_cache=True`（C 组必须产生新 packed）；D 组改用**非事实题**
（热岛题），`_opts_root()` 去掉 `no_cache` 并显式 `use_cache=True`。

**证据**：ffc 串行 25/25；预算 ¥1–2 档位下连续复跑仍 25/25。

## 3. 层1「未测出」的诚实说明（历史；V2.2.90+ 已用确定性回退修复）

probe case1 的研究层读数当时长期显示「未测出（settlement.total=0）」；
> **现状**：V2.2.90/96/97/102 已补三类回退，层1 整跑稳定 valued（见 docs/layer1_measurable_probe_20261030.md §7.14+）。
V2.2.60 复跑时检查 packed：

- `decidability.status=undecidable`，2 条 decidability 行均为 undecidable；
- `layer_artifacts={}`；引擎 layer view 的 settlement 为 answered=0 / total=0。

⇒ 这是**输入问题不可判定**导致的读数分母为 0（口径要求的「可指认原因」已给出），
不是读数通道坏了，也不是引擎回归。

**V2.2.67 更新（已定位并修复 probe 设计）**：层1 需要**上游层0**（route=1 单跑时
`views.1.candidates=0`）；且原题面「水的三态」即使带上游也不生成候选。probe case1 改为
route=0,1 + GDP 题面后可测（settle=0.000，valued；目标判定「判据样本不足」）。
详见 docs/layer1_measurable_probe_20261030.md。

## 4. 维护约定

1. 看到 23/1、29/1 先看是否并发（锁是否生效）、再看任务是否走了缓存复用；
2. 新增重资源判据脚本：启动即 `acquire_serial_lock("local_chain")`；
3. 子进程链路不要重复持锁（继承环境变量即可）；
4. 任何「单次变绿」不能当结论，需串行复跑或分布证据（见 probe 方差统计）。
