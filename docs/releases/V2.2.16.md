# Meta-DGTF 引擎 V2.2.16 发布说明（2026-10-28）

> 版本类型：**PATCH**（引擎）；App 2.0.37 不变。
> 生产文件：`dgtf_engine/dgtf_v2/engine/Meta-DGTF-V2.2.16.py`（`__version__ = "2.2.16"`）。
> V2.2.15 及更早只读保留；App 通过 glob 自动选用最高版本（无需改 App）。

## 1. 本版三个机制

### 1.1 JSON 期望显式声明通道（引擎 → shim → 服务约束解码）

- 问题（真实转储实测）：引擎 json_mode=True 的调用（dual_judge / he_amps / probe_* /
  phase_probe / self_check / decompose_* / assess_* 等 12+ 处）只把 JSON 期望写成
  response_format（OpenAI 语义）与 system 提示；本地 shim 不看它、服务也没有解码级约束
  ⇒ 0.5B 在长 prompt 下 **0% 以 { 开头**、全部撞 max_new（224）：解析不出结构、
  每跑几十次 json_repair、墙钟被拖长。
- 修法：LLM.call 把 json_mode 经 extra_body 显式摊到请求顶层（与 stage 同一条已打通的
  通道）→ shim 透传（兼容 response_format=json_object 的通用客户端）→ 服务端：
  1) 第 1 个 token 只在「解码后以 { 开头」的 token 集合里采样（mask 其余 logits）；
  2) JSON 一闭合即停（不再继续喷到上限）。
  纯函数在 `dgtf_local_llm/gates.py`（json_done / json_first_token_ids，零 torch）。
  服务开关 `DGTF_JSON_CONSTRAIN=0` 可关（A/B / 回滚用）。
- 受控 A/B（17 条固定真实 prompt、同 case 两次跑、服务每轮重启清缓存）：

| 指标 | 关闭 | 开启 | 变化 |
|---|---|---|---|
| JSON 解析成功率 | 35% | **59%** | +24pp |
| 以 { 开头率 | 35% | **100%** | +65pp |
| 撞 max_new 率 | 41% | **6%** | −35pp |
| gen_tokens 中位 | 93 | **23** | −75% |
| 单次 ms 中位 | 3842 | **1651** | −57% |
| 总墙钟（17 条） | 70.3s | **31.7s** | **−55%** |

### 1.2 本地端点自动切 self_check / dual_judge = local（适配器契约直连）

- 问题：默认档 "llm" 在本地链路上会经 shim 把**自然语言 prompt** 发给 LoRA 适配器，
  而适配器训练契约是结构化 payload（服务端只在 text 是 JSON 形状时才转）。
  实测经 shim 的 dual_judge **74/74 条输出都不是 JSON**（全在瞎编，还占墙钟）。
- 修法：main() 里对「本地端点 + 默认档 llm + 无显式 CLI」的两项自动切 local
  （引擎直连服务 /generate，按适配器契约发结构化 payload，带置信度门控与失败回退）。
  纯函数 `_auto_local_modes(cfg, explicit)` 可单测；显式 CLI / 配置非 llm 值一律尊重。
- 实测：切换后 dual_judge/self_check 不再进 shim（无 74/74 非 JSON 垃圾），
  自省走确定性核 + 本地判定；同一 route=1 任务候选数 0/1 → 2~8，
  质量旗标减少。e2e（App 真入口）墙钟 **106.7s**（V2.2.15 同判据 124.9~157.9s）。
- 顺带修 `_is_local_llm_endpoint` 的 IPv6 方括号解析（`http://[::1]:8773/v1`
  旧实现切成 "[" ⇒ 永远判非本地，与 docstring 承诺不符）。

### 1.3 本地直连调用的成本归因不再有暗路

- 问题：切 local 档后 self_check / dual_judge 走引擎直连 /generate（不经 OpenAI 客户端），
  LLM.call 的记账点看不到它们 ⇒ llm_calls / llm_by_stage 会把这两类调用整段漏掉
  （正是 V2.2.9 / V2.2.10 反复修的那类盲区）。
- 修法：新增 `LLM.record_local_call(stage, calls, tokens, ms)`（与 LLM.call 同分桶口径
  cost_bucket / ops / eval / stage_calls / stage_tokens / stage_ms）；
  `_self_check_local` 与 `_dual_judge_local` 成功路径记账；dual_judge 回退路径保留
  prompt_tokens/gen_tokens/ms 读数。

## 6. 已知边界

- 结构有效 ≠ 语义正确：0.5B 的语义能力仍是层 1/both/all 达成的唯一主瓶颈；
- 强制 { 开头对「适配器契约不符」的 stage 只会让它**失败得更快**（不是变对）——
  这类 stage 的真正修法是 1.2 的 local 直连（已做）；
- 本地档定位仍是零成本链路验证 / 离线可用，不是生产质量档。
